# 항공·여객선 API 실응답 감사 v0.1 / Gateway API Audit v0.1

최신 실행 / Latest run: 2026-11-12 22:07 KST

## 결론 / Decision

G1에서 한국공항공사 항공 2종과 한국해양교통안전공단 여객선 2종을 현재 공공데이터포털 서비스키로 실제 호출했다. 네 호출 모두 HTTP 응답을 받았지만 데이터 레코드는 확보하지 못했다. 감사 구조와 비밀값 차단 검사는 통과했으나 실제 피처 연동 준비상태는 4종 모두 `blocked_or_limited`다.

항공 2종은 HTTP 403과 제공자 코드 `30 SERVICE_KEY_IS_NOT_REGISTERED_ERROR`를 반환했다. 활용신청 승인 화면과 해당 서비스의 64자리 일반 인증키를 확인한 뒤 공식 `/info` operation에 직접 재호출했지만 같은 코드가 반환됐다. 같은 환경에서 기상청 API는 정상 응답했으므로 코드·인코딩 문제로 간주하지 않고 제공자 권한 동기화 차단으로 남겼다.

여객선 2종은 공공데이터포털에 표시된 호출 주소에서 HTTP 400과 제공자 코드 `12 NO_OPENAPI_SERVICE_ERROR`를 반환했다. 운항 스케줄 API는 여객선명도 필수 입력이라 제주 전체를 조회하려면 선박 목록 또는 별도 노선 카탈로그가 먼저 필요하다. 공식 활용가이드의 실제 operation 경로와 서비스 상태를 제공기관에 확인하기 전에는 피처로 사용하지 않는다.

## 의미 구분 / Semantics

- 실시간 항공편은 도착 예정·변경·지연·결항 근거다. 승객 수가 아니다.
- 시간대별 도착 승객 API는 집계값 후보지만 실제 응답 기간과 필드 의미를 확인하기 전에는 사용할 수 없다.
- 여객선 운항 스케줄의 여객정원은 최대 수용량이며 실제 탑승객 수가 아니다.
- 월별 운송인원은 과거 기준선이며 현재 유입량이 아니다.

따라서 실제 응답이 확보된 뒤에도 네 원천을 하나의 `입도객 수`로 합치지 않는다. `actual_aggregate`, `schedule`, `capacity_proxy`, `historical_baseline`을 분리하고 공항·항만 주변 `gateway_inflow_pressure`의 근거로만 사용한다.

## 안전장치 / Guardrails

- HTTP 오류 안의 JSON·XML 제공자 코드를 별도로 추출
- 오류 본문에서 서비스키를 마스킹
- 운항편수·정원·월별 통계를 실제 실시간 승객 수로 표시하지 않음
- 제주 신호가 실제 레코드에서 확인되기 전에는 준비 완료로 판정하지 않음
- 여객선명 필수 계약과 전체 제주 조회 불가 가능성을 명시적 blocker로 기록
- 접근 실패를 0편·0명으로 변환하지 않음

## 후속 조치 / Follow-up

1. 항공 API ID `15163384`, `15167062`의 승인·인증키 연결 상태를 공공데이터 활용지원센터에 문의
2. KOMSA API ID `15142302`, `15142310`의 실제 operation 등록 상태를 제공기관에 문의
3. 권한·서비스가 복구될 때까지 G2 관문 유입압력은 `unavailable`로 유지

인증키를 바꾸거나 실패를 0편·0명으로 변환하지 않는다. G1은 외부 서비스 차단으로 고정하고, 독립적으로 진행할 수 있는 기상 기반 F1 우선순위 시나리오를 먼저 구축한다.
