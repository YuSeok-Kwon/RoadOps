# [2026-11-16] 제주 RoadOps 프로젝트 6부 — 화면이 있으면 공무원이 바로 사용할 수 있을까

### **요약 & 나만의 인사이트**

지난 작업에서 RoadOps는 현재·1·3·6시간 도로위험, 팀별 순찰 경로, 도로통제·폭우 What-if 재계획을 제주 지도 위에 올렸다. 이번에는 그 지도를 단순한 조회 화면에서 자원 확인, 업무 수정, 안전 재검증, 담당자 승인과 감사 로그까지 이어지는 운영 웹으로 확장했다.

처음에는 지도 옆에 승인 버튼 하나를 붙이면 될 줄 알았다. ~~버튼을 누르면 정책이 생기는 줄 알았다.~~ 하지만 자원 수나 담당팀이 바뀌었는데 예전 경로를 그대로 승인할 수는 없다. 데이터가 오래됐거나 API가 실패했는데도 계획이 멀쩡해 보이면 더 위험하다.

이번 작업에서 가장 크게 배운 점은 **실용성은 사용자가 많은 것을 할 수 있는지보다, 잘못된 것을 확정하지 못하게 막는지에서 드러난다**는 것이다.

그래서 검증된 `안전 우선`·`균형 운영` 두 계획만 승인할 수 있게 했다. 자원·업무를 바꾸면 기존 경로를 숨겨서 새 계획처럼 보이지 않게 했다. 대신 `백엔드 재계획이 필요합니다`라고 멈춘다.

마지막으로 API 실패, 기한이 지난 데이터, 잘못된 도로 링크, 최적화 불능, 설명 생성 실패를 인위적으로 주입했다. 6개 시나리오의 53개 안전 검사는 모두 통과했고, 어떤 경우에도 자동 출동은 허용하지 않았다.

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- 팀·차량·인원·근무시간과 현장 업무를 한 화면에서 확인·편집
- `안전 우선`·`균형 운영` 계획 비교와 팀 경로 지도 연동
- 필수 업무 제외, 차량 정원, 비가용팀, 업무 수 제약 재검증
- 미계산 수정안의 승인 차단과 기존 경로 숨김
- 데이터·이동시간·현장 재확인 3개 안전확인
- 담당자·승인 사유·계획 지문과 브라우저 감사 로그
- API·신선도·링크·최적화·설명 장애 주입 평가

**문제 상황**

- 기존 지도는 위험도와 팀 경로를 보여주지만, 담당자가 자원 상태를 확인하고 계획을 승인하는 흐름은 없었다.
- 차량 상태나 인원을 수정해도 기존 경로가 남아 있으면, 사용자가 수정된 조건으로 다시 계산된 결과라고 오해할 수 있었다.
- 필수 업무를 제외하거나 비가용팀에 업무를 배정해도 버튼만 누를 수 있다면 승인 절차의 의미가 없었다.
- 승인 후 입력이 바뀌었는데 예전 승인 상태가 계속 남으면 현재 계획과 승인 대상을 구분할 수 없었다.
- API 실패나 오래된 스냅샷을 만나도 어떤 상태로 전환할지 한곳에 고정된 장애 정책이 필요했다.

**시도한 방법 & 탐색 과정**

- **사용 흐름을 `보기`에서 `검토하고 책임지기`로 바꾸었다.**

웹의 순서를 화면 구성요소가 아니라 현장 의사결정 순서에 맞춰다.

```text
1. 자원 확인
2. 현장 업무·담당팀·고정·제외 확인
3. 계획 제약 재검증
4. 데이터·이동시간·현장 재확인
5. 담당자·승인 사유 입력
6. 계획 지문·승인 기록·감사 로그 생성
```

승인 버튼은 제약 오류가 0건이고, 3개 안전확인이 모두 완료됐으며, 담당자와 승인 사유가 입력된 뒤에만 활성화된다.

- **수정과 재계산을 같은 행동으로 간주하지 않았다.**

웹 MVP는 브라우저 안에서 Python 최적화기를 다시 실행하지 않는다. 따라서 자원 수, 인원, 근무시간, 담당팀이나 제외 조건을 바꾸면 기존 경로를 새 결과라고 표시하지 않는다.

```text
수정 발생
  → 기존 경로 숨김
  → RESOURCE_REPLAN_REQUIRED 또는 ROUTE_REPLAN_REQUIRED
  → 승인 차단
  → 백엔드 재계획 요구
```

예를 들어 동부팀 인원을 2명에서 1명으로 바꾸면 `RESOURCE_REPLAN_REQUIRED`가 발생하고 승인이 막힌다. 담당팀을 바꾸거나 필수 업무를 제외해도 동일하다. 수정을 입력받는 것과 수정된 계획을 계산했다는 것은 전혀 다른 상태다.

- **승인을 버튼 상태가 아니라 계획 스냅샷에 묶었다.**

현재 계획의 자원, 업무, 배분안, What-if 시나리오를 정렬한 뒤 결정적 `workflowFingerprint`를 만든다. 승인 기록에는 담당자, 사유, 시각과 함께 이 지문을 남긴다.

승인 뒤 인원이나 업무를 바꾸면 새 계획 지문이 만들어진다. 이전 승인은 삭제하지 않지만 현재 계획의 승인으로도 표시하지 않는다. “누가 승인했는가”만큼 “무엇을 승인했는가”가 중요했다.

- **장애 종류별로 안전한 상태를 다르게 정의했다.**

모든 실패를 같은 오류 창으로 처리하지 않았다. 사용 가능한 최근 캐시가 있는 API 실패는 `degraded`로 계속하되 캐시 나이와 실시간이 아님을 표시한다. 캐시가 없거나 오래되었으면 `hold`로 중단한다. 참조망에 없는 도로 링크는 `excluded`로 분리하고 원본 근거를 보존한다.

| 장애 | 안전 상태 | 복구 행동 |
|---|---|---|
| API 실패 + 30분 캐시 | `degraded` | 캐시 재생, 실시간 표현 금지 |
| API 실패 + 사용 가능한 캐시 없음 | `hold` | 신선한 데이터 대기 |
| 121분 경과 스냅샷 | `hold` | 점수·배분 중단, 재수집·수동 검토 |
| 잘못된 도로 링크 | `excluded` | 순위에서 제외, 원본·사유 보존 |
| 실행 가능한 배분안 없음 | `hold` | 하드 제약 유지, 수동 개입 |
| 설명 생성 실패 | `degraded` | 검증된 Tool 결과만 템플릿으로 복사 |

**최종 해결 및 적용 코드**

웹 승인 정책의 핵심은 “수정 가능”과 “승인 가능”을 분리한 것이다.

```javascript
// 운영 웹 승인 정책 개념 요약
const approvalReady =
  errors.length === 0 &&
  acknowledgements.dataQuality &&
  acknowledgements.travelEstimate &&
  acknowledgements.fieldCheck &&
  approverName.trim().length >= 2 &&
  approvalReason.trim().length >= 5;

if (resourceChanged || taskChanged) {
  hideUnvalidatedRoute();
  blockApproval("BACKEND_REPLAN_REQUIRED");
}
```

장애 평가는 각 시나리오가 예상한 상태와 복구 행동으로 전환되는지 검사한다.

```python
# 장애·복구 평가 개념 요약
checks = {
    "expected_safe_state": actual_state == expected_state,
    "expected_recovery_action": actual_action == expected_action,
    "automatic_dispatch_blocked": not automatic_dispatch_allowed,
    "manual_approval_required": manual_approval_required,
    "failed_value_not_imputed_as_zero": not imputed_as_zero,
    "recovery_evidence_present": bool(recovery_evidence),
}
```

설명 생성기가 실패했을 때도 LLM이 다시 임의의 설명을 만들게 하지 않았다. 이미 검증된 Tool 결과의 대안 ID, 배정·미배정 건수, 커버리지, 이동시간, 제약 위반과 한계만 결정적 템플릿으로 복사한다. Tool 결과도 유효하지 않으면 설명을 만들지 않고 멈춘다.

**실제 검증 결과**

웹 흐름은 다음 순서로 직접 검증했다.

| 항목 | 결과 |
|---|---:|
| 검증된 안전 우선 계획 | 오류 0건, 주의 2건 |
| 승인 전 필수 안전확인 | 3개 |
| 정상 승인 후 감사 이벤트 | 안전확인 3 + 검증 1 + 승인 1 |
| 인원 2명→1명 수정 | `RESOURCE_REPLAN_REQUIRED`, 승인 차단 |
| 이전 승인·현재 계획 지문 | 별도 보존 |
| 390×844 모바일 가로 넘침 | 0건 |

장애·복구 평가는 저장된 기준 산출물에 6개 장애를 주입했다. 기준 산출물은 위험점수 25행, 도로 참조 링크 136개, 이동시간 경로 108개, 최적화 대안 2개였다.

| 평가 | 결과 |
|---|---:|
| 장애 주입 시나리오 | 6 / 6 통과 |
| 안전 정책 검사 | 53 / 53 통과 |
| 자동 출동 허용 | 0건 |
| Python 전체 자동화 테스트 | 152개 통과 |

이 숫자는 실제 제주 운영 장애 6건을 해결했다는 뜻이 아니다. 저장된 데모 산출물에 통제된 실패 조건을 주입했을 때 정해진 안전 정책이 작동했다는 뜻이다. 실제 API 장시간 장애, 다중 장애, 서버 재시작 후 복구시간은 아직 측정하지 않았다.

**개발 중 발견한 실패 사례**

- **수정된 조건과 예전 경로의 혼재:** 초기 화면에서는 인원을 바꾸어도 지도의 경로가 남아 있었다. 수정된 계획처럼 오해할 수 있어 기존 경로를 숨기고 승인을 막았다.
- **필수 업무 제외:** 현장 업무를 제외하는 UI가 있어도 필수 업무는 제외할 수 없다. `MANDATORY_TASK_EXCLUDED`로 승인을 차단했다.
- **승인 후 조건 변경:** 예전 승인 표시가 남아 현재 계획도 승인된 것처럼 보였다. 계획 지문을 생성해 승인 대상을 분리했다.
- **미래 시각의 캐시:** 시계 오차로 캐시 시각이 현재보다 뒤로 잡히면 나이가 0분으로 보일 수 있었다. 미래 시각 캐시는 신선한 데이터로 인정하지 않도록 경계값 테스트를 추가했다.
- **설명 실패 후 다시 생성:** 설명을 재시도하다가 검증되지 않은 숫자가 들어갈 수 있었다. 새 추론 대신 검증된 구조화 결과만 복사하는 템플릿을 선택했다.

### **배운 점 / 재발 방지 노트**

- **입력을 받았다고 재계산한 것이 아니다:** 수정된 조건에 맞는 경로와 지표가 없으면 계획을 승인하면 안 된다.
- **승인은 사람 이름만 남기는 절차가 아니다:** 계획 지문과 사유, 안전확인, 검증 결과가 함께 남아야 한다.
- **실패별 안전 상태는 다르다:** 최근 캐시로 제한적으로 계속할 수 있는 실패와 즉시 멈춰야 하는 실패을 분리해야 한다.
- **결함값을 0으로 바꾸는 것은 복구가 아니다:** 실패과 미수집은 안전을 증명하지 않는다. 보류·제외·불확실성으로 남겨야 한다.
- **편리함은 안전장치를 삭제하는 것이 아니다:** 사용자가 왜 멈춰는지, 무엇을 확인하면 다시 진행할 수 있는지 알 수 있게 만드는 것이다.

### **새롭게 알게 된 점**

**1. 승인 가능 상태는 하나의 파생변수였다**

- 제약 검증, 안전확인, 담당자, 승인 사유가 모두 있을 때만 `approvalReady=true`다.
- 버튼 활성화 조건을 UI 카피와 따로 관리하지 않고 같은 검증 결과에서 만들었다.
- 하나라도 바뀌면 다시 검증해야 한다.

**2. 지문은 승인의 대상을 정의했다**

- 담당자와 시각만으로는 어떤 자원·업무·배분안을 확인했는지 알 수 없다.
- 동일한 계획 상태는 정렬 순서와 관계없이 같은 지문을 만든다.
- 입력이 바뀌면 기존 승인을 삭제하지 않고 다른 스냅샷으로 분리한다.

**3. 장애 평가는 “에러가 났다”보다 이후 행동을 검증했다**

- API 실패 사실만 확인하는 것으로는 부족하다.
- 계속해도 되는지, 순위와 배분을 막았는지, 원본 근거를 남겼는지를 각각 확인해야 한다.
- 실패 후에도 자동 출동과 실패값 0 대체는 모두 금지했다.

### **학습 중 어려웠던 부분**

**수정을 어디까지 허용할지**

- 편집 기능이 있다고 모든 수정안을 즉시 승인할 수 있게 하면 안 됐다.
- 단순 수정, 제약 검증, 경로 재계산을 다른 단계로 구분해야 했다.
- 현재는 수정을 받되 재계산되지 않은 결과를 승인하지 못하게 하는 보수적 방식을 선택했다.

**지도가 완성도를 과장하는 문제**

- 웹 화면이 자연스럽게 동작할수록 실제 운영 서비스처럼 보였다.
- 하지만 위험 데이터는 저장 스냅샷이고, 이동시간은 실시간 ETA가 아니며, 승인 로그는 브라우저에만 남는다.
- 화면이 정교할수록 한계를 숨기기보다 더 눈에 띄게 보여줘야 했다.

**실제 복구력과 시뮬레이션 통과를 구분하기**

- 6개 시나리오 통과는 복구 정책의 결정성과 안전 전환을 검증한다.
- 실제 서버의 재시도 시간, 복구 시간, 타임아웃과 부분 응답 조합을 측정한 것은 아니다.
- 테스트 통과를 운영 SLA나 실제 현장 신뢰성으로 과장하면 안 된다.

### **AI를 어떻게 활용했나**

AI에게 승인 가능 여부를 느낌으로 판단하게 하지 않았다. 대화로 사용자의 검토 순서, 수정 후 무효화해야 할 상태, 장애별 안전 상태와 증거 조건을 분해했다. 이후 React 운영 화면, 제약 검증기, 계획 지문·감사 로그 로직과 Python 장애 주입 평가를 구현하고 경계값을 테스트로 고정했다.

현재 승인 가능 여부, 지문, 장애 복구 상태와 결정적 설명 대체문은 JavaScript·Python 규칙이 계산한다. LLM은 사용자의 다양한 요청을 구조화하고 검증된 Tool 결과를 설명하는 층으로 추가할 계획이다. 설명 생성이 실패했다고 점수나 배치를 다시 추측하지는 않는다.

### **다음에 적용해 볼 것**

**수정 후 실제 재최적화 연결**

- 현재 웹은 수정된 입력을 검증하고 승인을 차단하지만 새 경로를 계산하지는 않는다.
- Python 최적화 엔진을 웹 API로 연결해 수정→재계획→재검증→승인 흐름을 완성한다.
- 재계획 전후의 작업, 이동시간, 커버리지와 미배정 사유를 함께 보여준다.

**감사 로그와 복구 상태 서버 저장**

- `localStorage`에만 남는 승인·감사 기록을 서버 저장소로 옮긴다.
- 재시작 후에도 계획 지문과 승인 이력을 복구할 수 있게 한다.
- 동시 수정, 권한, 승인 취소와 재승인 정책을 추가한다.

**실서버 장애·복구 측정**

- 외부 API 타임아웃·부분 응답·다중 장애를 실제 서버 환경에서 주입한다.
- 탐지시간, 복구시간, 캐시 적중률과 수동 개입 건수를 측정한다.
- 현장 사용자가 `degraded`·`hold`·`excluded`를 올바르게 이해하는지 과업 테스트를 진행한다.

계획을 잘 만드는 시스템과, 잘못된 계획을 승인하지 못하게 막는 시스템 중 현장에서는 어느 쪽이 더 중요할까?
