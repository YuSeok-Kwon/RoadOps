# [2026-11-20] 제주 RoadOps 프로젝트 8부 — 120분을 넘긴 계획에서 배운 것

### **요약 & 나만의 인사이트**

RoadOps의 마지막 시연 결과는 **125.6분**이었다. 사용할 수 있는 시간은 120분이었다.

용담에서 출발한 팀이 광령리 점검을 마친 뒤, 남은 경로의 1100로 일부가 통제됐다고 가정했다. 소길리와 예래동 방문을 모두 유지하면 가용 시간을 5.6분 넘길 것으로 계산됐다. 화면에는 초과 예상 시간이 표시됐고, 해당 안을 바로 확정하는 버튼은 비활성화됐다.

공모전 발표를 마무리하는 장면으로는 조금 의외의 결과였다. 하지만 이 결과에서 내가 만들고 싶었던 기능이 가장 분명하게 드러났다. 담당자는 다음 이동을 시작하기 전에 시간 부족을 확인하고, 근무시간을 조정하거나 지원을 요청할지 검토할 수 있었다.

여기까지 오기 위해 마지막으로 다시 확인해야 했던 것은 경로와 시간이었다. 처음 준비한 화면에서는 통제를 반영했다는 설명과 달리 지도 경로가 그대로였기 때문이다.

이번 글은 그 문제를 다시 검증한 과정과, 제주 공공데이터를 점검 업무로 연결하며 배운 점을 정리한 RoadOps의 마지막 개발 기록이다.

### **프로젝트: 제주 도로관리 운영 보조 Agent — RoadOps**

RoadOps는 도로관리 담당자가 점검 우선순위를 정하고, 가용 인원과 시간 안에서 방문 계획을 검토하도록 돕는 프로젝트다. 출발 후 도로가 통제되면 완료한 점검을 보존하고 남은 이동 경로를 다시 계산한다.

7부에서는 실제 배경지도, 공개자료 기반 출발 거점, 담당자의 우선순위 조정과 재배분까지 정리했다. 이후에는 점수의 판단 기준을 담당자가 설정하도록 바꾸고, 제주데이터허브 자료를 점검 항목에 연결했다. 브라우저에서도 통제 구간을 제외한 도로망을 직접 탐색하도록 확장했다.

마지막 작업에서는 이 기능들을 한 사람의 업무 순서로 연결했다.

```text
자료와 점검 근거 확인
  → 우선순위 기준 설정
  → 인원·시간·방문 조건 입력
  → 방문 계획 검토
  → 점검 진행 중 통제 발생을 가정
  → 완료 기록을 유지하고 남은 경로 재계산
  → 초과 시간 확인과 담당자 검토
```

### **오늘 해결한 문제 / 이슈**

- 제주데이터허브의 과거 자료가 현장의 점검 항목으로 이어지도록 구성했다.
- 점수에 반영한 근거와 자료가 없는 항목을 구분했다.
- 실제 이동 경로가 달라지는 통제 사례를 찾고, 전후 시간을 같은 기준으로 계산했다.
- 가용 시간을 초과하는 경우에도 필요한 시간을 보여주되, 검토 없이 확정되지 않도록 했다.
- 실제 화면과 검증 결과를 15장 발표 흐름으로 정리했다.

### **시도한 방법 & 탐색 과정**

**1. 과거 통계를 점검 항목으로 연결했다**

데이터를 확보하고도 사용처가 모호한 순간이 있었다. 노면 상태별 사고 통계나 자연재해위험개선지구 목록을 보여주면 담당자는 그다음에 무엇을 해야 할까.

노면 상태에 따라 물고임, 배수, 결빙, 제설 상태 등을 확인하는 항목을 제안하고, 담당자가 선택한 도로의 점검 계획에 반영할 수 있도록 했다. 반영할 때는 사용한 자료의 출처와 기간도 함께 남겼다.

예상 노면은 거점별 기상 관측·예보를 이용한 규칙으로 선택한다. 담당자가 현장 상황을 알고 있다면 직접 수정할 수 있고, 화면에는 담당자가 수정한 값이라는 표시를 남긴다. 거점의 날씨로 추정한 상태이므로 도로 노면을 직접 측정한 값으로 표현하지 않았다.

과거 자료를 해석하는 범위도 좁혔다. 이번에 확보한 젖음·습기 조건의 2005~2020년 집계에는 사고 7,218건과 사망자 226명이 있었다. 이 값으로 계산한 약 3.13명은 **사고 100건당 사망자 수**다. 통행량과 젖은 노면에 노출된 시간을 모르므로 사고 발생확률로 바꿀 수는 없다.

재해지구 자료에서는 지정 해제와 정비 완료를 구분했다. 광령리 관련 자료에는 해제 이력이 있었고, 이를 확인해 자동 점검 제안에서 제외했다. 같은 행정지역에 지구가 있다는 사실만으로 특정 도로가 위험하거나 통제됐다고 판단하지도 않았다.

이렇게 출처와 적용 범위를 정리하니 자료가 담당자의 점검 준비에 어떻게 쓰이는지 설명할 수 있었다.

**2. 점수의 기준을 담당자가 확인하고 바꾸도록 했다**

이번 버전에서는 담당자가 점수에 포함할 항목과 배점을 정할 수 있다. 자료가 일부 없어도 확인된 근거를 기준으로 환산할지, 선택한 근거가 모두 있어야 점수를 계산할지도 선택한다. 수동 화면과 자동 제안은 같은 설정을 사용한다.

여기서 구분해야 했던 상태는 세 가지였다.

| 상태 | 의미 |
| --- | --- |
| 확인된 0 | 자료를 확인했지만 해당 항목의 추가 기여가 없음 |
| 자료 없음 | 판단에 필요한 값을 확인하지 못함 |
| 해당 없음 | 그 도로에 해당 항목을 적용하지 않음 |

이 상태들을 모두 0으로 처리하면, 근거가 부족한 도로가 낮은 우선순위로 보일 수 있다. 그래서 최종 점수와 함께 어떤 근거가 얼마나 반영됐는지 확인하도록 했다. 점수는 점검 우선순위 지수이며 사고 발생확률을 뜻하지 않는다.

발표자료를 확인하면서 또 하나 배웠다. 같은 ‘평화로’라는 이름 옆에 46.1점과 44.0점이 표시돼 처음에는 자료 시점이 다른 것으로 의심했다. 원본을 대조해 보니 같은 시점의 **서로 다른 도로 구간**이었다. 이후에는 도로명뿐 아니라 구간 식별자와 위치를 함께 확인했다.

**3. 통제 전후 지도가 같았던 사례를 다시 검증했다**

처음 만든 발표 화면에는 ‘통제 반영 순찰코스’라는 제목이 있었다. 방문지는 광령리, 소길리, 예래동이었고 통제 전후에 그대로 유지됐다. 방문 순서가 같아도 이동 경로는 달라질 수 있으므로, 목록만으로 문제가 있다고 판단할 수는 없었다.

그런데 지도의 선도 같았다. 동일한 도로망과 시간 계산 방식으로 다시 비교하니, 그 통제 조건에서는 실제 이동 경로가 바뀌지 않았다. 이 화면으로 우회 경로 변경을 설명할 수는 없었다.

시연 사례를 다시 정했다. 통제 전 경로가 실제로 지나는 1100로의 약 398m 방향 구간을 선택하고, 해당 구간을 제외했을 때 다른 길을 찾는지 확인했다. 이는 **통제 발생을 가정한 검증 시나리오**이며 실제 도로의 현재 통제 상황은 아니다.

완료된 광령리 점검 기록과 남은 소길리·예래동의 방문 순서는 유지했다. 그 상태에서 광령리에서 소길리로 가는 경로는 같고, 소길리에서 예래동으로 가는 경로가 달라지는 것을 확인했다.

### **같은 기준으로 계산하니 총 125.6분이 필요했다**

경로가 달라졌다는 사실을 확인한 다음에는 시간을 비교했다. 저장된 최초 계획과 새 우회 계산의 시간 산정 방식이 다르면, 숫자의 차이를 통제 영향으로 해석할 수 없기 때문이다.

이번 비교는 2026년 11월 19일 17:40 저장 자료를 사용했다. 용담팀 2명, 가용 시간 120분 조건에서 광령리 점검을 마친 시점을 기준으로 삼았다. 통제 전과 후 모두 같은 2026년 10월 14일 기준 도로망과 제한속도 기반 비용으로 남은 경로를 다시 계산했다. 제한속도가 없는 구간에는 같은 기본속도 규칙을 적용했다.

완료 소요시간 **39.8분은 양쪽에 동일하게 둔 시연 입력값**이다. 실제 현장에서 측정한 시간이 아니다. 남은 두 곳의 점검 시간은 각각 15분으로 고정했다.

| 구분 | 통제 전 | 통제 후 |
| --- | ---: | ---: |
| 광령리 점검까지 완료한 시간 | 39.8분 | 39.8분 |
| 광령리 → 소길리 이동 | 5.8분 | 5.8분 |
| 소길리 점검 | 15.0분 | 15.0분 |
| 소길리 → 예래동 이동 | 25.0분 | 50.0분 |
| 예래동 점검 | 15.0분 | 15.0분 |
| **총 예상 소요시간** | **100.6분** | **125.6분** |

표시는 소수 첫째 자리로 반올림했다. 원계산 결과는 통제 전 100.570분, 통제 후 125.613분이었다. 통제에 따른 추가 예상 시간은 25.043분, 가용 120분 대비 초과 예상 시간은 5.613분이다.

이전 최초 계획 화면의 101.2분은 이번 비교의 기준으로 사용하지 않았다. **100.6분도 광령리 완료 시점에서 같은 기준으로 다시 계산한 값**이다.

또한 이 추정에는 실시간 혼잡, 신호 대기, 회전 제한, 거점 복귀시간이 포함되지 않는다. 이번에 확인한 것은 정해진 도로망과 비용 조건에서 통제 전후 경로와 시간이 어떻게 달라지는지다.

### **시간 초과를 다음 판단에 연결했다**

이 비교에서는 남은 방문을 모두 유지했다. 그 결과 120분 안에 끝낼 수 없는 것으로 나타났고, 이 상태를 화면에 그대로 보여주기로 했다.

```text
이미 사용한 시간       39.8분
남은 이동·점검 시간   +85.8분
─────────────────────────
총 예상 소요시간      125.6분
가용 시간 대비 초과     5.6분
```

처음에는 가용 시간 안에 들어오는 계획을 만드는 데 집중했다. 마지막 시연에서는 통제로 조건이 바뀌었을 때 **현재 계획에 얼마나 더 필요한지 알려주는 것**도 업무 지원의 중요한 결과라는 점을 배웠다.

### **최종 해결 및 검증**

계산값만 확인하지 않고 원본 도로 구간, 지도 표시, 사용자 동작까지 연결해 점검했다.

| 검증 대상 | 확인한 내용 |
| --- | --- |
| 전후 경로 | 통제 전에는 해당 구간을 지나고, 통제 후에는 제외되는지 확인 |
| 독립 계산 | JavaScript 결과와 별도 Python 계산의 전후 네 이동 구간에서 도로 구간 목록과 시간이 일치 |
| 지도 표시 | 실제 경로선의 변화와 전후 지도 범위·배율의 동일성 확인 |
| 완료 기록 | 광령리 완료 기록과 공통 소요시간 유지 |
| 사용자 동작 | 실제 입력과 계산, 초과 표시, 검토용 안의 확정 차단 확인 |

11월 20일 이 작업 단위에서 웹 테스트 46개와 앱 빌드를 통과했다. 통제해도 경로가 바뀌지 않는 기존 사례와 목적지 자체가 통제되는 경우도 회귀 테스트에 포함했다. 경로가 바뀌는 결과만 정답으로 취급하지 않기 위해서다.

발표에 사용한 지도와 계산 결과는 실제 앱에서 버튼을 눌러 캡처했다. 지도 위에 우회선을 따로 그리거나 이미지의 수치를 바꾸지 않았다. 어두운 화면과 좁은 화면에서도 결과를 확인했다.

이 검증으로 확인한 범위는 구현의 계산 일관성과 화면 동작이다. 실제 현장의 이동시간 오차나 점검 효과는 후속 현장 평가가 필요하다.

### **발표자료를 정리하며 사용자 흐름도 다시 확인했다**

15장에 내용을 정리하면서 기능별 화면을 담당자의 업무 순서로 배치했다. 자료를 확인하고, 판단 기준과 자원을 설정하고, 최초 계획을 검토한 뒤, 통제 상황에서 계획을 다시 확인하는 흐름이다.

점수 옆에는 산정 근거가 필요했고, 방문 계획 옆에는 인원과 시간이 필요했다. 우회 결과에는 통제 전후의 차이와 초과 예상 시간이 함께 있어야 했다. 화면만 놓고 설명할 수 없는 부분을 찾을 때마다 실제 계산과 문구를 다시 확인했다.

특히 ‘예상’, ‘완료’, ‘미확인’처럼 짧은 상태 표현의 의미를 통일하는 데 시간이 들었다. 개발 환경에서 확인한 기능과 현장 도입 뒤 검증해야 할 효과도 구분했다. 발표자료를 만들며 프로젝트의 설명 범위를 한 번 더 정리할 수 있었다.

### **AI를 어떻게 활용했나**

AI는 데이터 사용 범위를 정리하고, 코드와 테스트를 작성하고, 실제 화면을 검토하며 설명을 다듬는 데 활용했다. 오류가 보이면 그 화면이 어떤 입력과 계산을 거쳐 나왔는지 다시 추적하도록 했다.

통제 전후 경로가 같았을 때도 구현 코드, 도로 구간 목록, 별도 계산 결과, 브라우저 화면을 차례로 대조했다. AI가 작성한 설명도 이 검증을 통과한 범위에 맞춰 수정했다. 어떤 결과를 시연할지, 무엇을 근거로 주장할지는 내가 계속 확인해야 했다.

현재 앱의 우선순위와 경로는 규칙·통계·경로 탐색 코드가 계산한다. **실행 중 LLM이 요청을 해석하고 도구를 호출하는 연동은 아직 구현하지 않았다.** 개발에 AI를 활용한 사실과 서비스에 LLM을 연결한 상태를 구분해 발표에도 반영했다. 향후 연동 범위는 요청 구조화와 검증된 도구 결과의 설명으로 두고 있다.

### **현재 완성된 것과 아직 완성되지 않은 것**

현재는 개발 환경에서 자료 조회, 점검 항목 반영, 담당자 기준에 따른 우선순위 계산, 방문 계획, 통제 구간 우회와 초과 시간 표시까지 실행할 수 있다. 발표용 저장 입력과 검증 자료도 보존했다.

현장 도입을 위해서는 다음 단계가 남아 있다.

| 남은 작업 | 확인할 내용 |
| --- | --- |
| 실제 운영 조건 확인 | 거점 출발 위치, 점검 시간, 복귀 조건, 담당자의 승인 절차 |
| 현장 시간 검증 | 혼잡·신호·회전 제한 등을 반영한 추정값과 실제 이동시간의 차이 |
| 사용자 평가 | 계획 작성 시간, 필수 점검 누락, 통제 이후 재계획에 걸리는 시간 |
| 운영 환경과 기록 관리 | 센터 PC 성능, 서버 저장, 기관 권한과 승인 체계 연계 |
| LLM 연동과 평가 | 요청 구조화, 도구 호출, 결과 설명과 오류 처리 |

예보를 반영한 미래 시점의 우선순위도 사고 예측 정확도를 검증한 결과로 발표하지 않았다. 같은 버전과 조건으로 평가 자료를 더 쌓아야 한다.

### **배운 점 / 재발 방지 노트**

**비교할 때는 바뀐 조건을 좁혀야 한다.** 통제 효과를 보려면 완료 시간, 방문 대상, 점검 시간, 도로망과 이동 비용을 같게 둬야 했다. 서로 다른 방식으로 계산한 숫자 사이에서는 통제 때문에 얼마나 더 걸리는지 읽을 수 없었다.

**재계획에서는 유지할 기록을 먼저 정해야 한다.** 이미 끝낸 점검과 사용한 시간을 보존해야 남은 업무를 현실적으로 계산할 수 있었다. 방문 순서와 이동 경로 역시 별도로 비교해야 했다.

**화면의 표현도 검증 대상이다.** ‘통제 반영’이라는 제목만으로 우회가 구현됐다고 볼 수 없었다. 반대로 같은 도로명에 다른 점수가 붙었다고 해서 오류라고 단정할 수도 없었다. 실제 구간과 상태를 확인하는 절차가 필요했다.

### **새롭게 알게 된 점과 이후의 과제**

처음에는 데이터를 연결하면 더 나은 계획을 만들 수 있을 것이라고 생각했다. 작업을 이어가면서 데이터의 기준시각, 위치 단위, 누락 상태, 계산 조건을 하나씩 정해야 했다. 어느 자료를 어디까지 사용할 수 있는지 정하는 일이 구현의 상당 부분이었다.

마지막에는 결과를 보여주는 방식까지 같은 질문이 이어졌다. 총 125.6분이라는 값을 보고 담당자가 무엇을 판단할 수 있는지, 지금 확정해도 되는지를 화면에서 읽을 수 있어야 했다.

후속 작업의 우선순위는 실제 담당자의 업무 조건을 확인하고, 그 조건에서 계획을 검토하는 과정을 평가하는 것이다. 기능을 더 연결하더라도 그 판단 기준은 유지하고 싶다.

### **RoadOps 개발 기록을 마치며**

이번 개발 기록은 여기서 마무리한다. 공개 데이터를 조사하는 데서 시작해, 담당자가 점검 계획을 세우고 도로 통제 이후의 시간까지 확인하는 시연을 완성했다.

가장 기억에 남는 숫자는 125.6분이다. 계획의 한계가 드러났고, 그 한계를 다음 이동 전에 확인할 수 있었다. RoadOps가 담당자에게 제공하려는 도움을 그 장면으로 설명할 수 있게 됐다.

마지막 슬라이드에는 이 문장을 남겼다.
