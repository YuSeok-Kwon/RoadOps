AI와 함께 제주 통합 도로안전 관제 Agent를 만들고 있습니다 — RoadOps 6부

“위험을 발견한 다음, 누가 어디부터 확인해야 할까?”

RoadOps 웹을 직접 데모해 보니 계산이 맞는 것과 현장에서 이해하기 쉬운 것은 전혀 다른 문제였습니다.

빨강·주황·파랑 도로선과 팀 경로가 겹쳐 무엇이 위험이고 무엇이 이동 경로인지 구분하기 어려웠습니다. 출발지는 왜 그곳인지 설명할 수 없었고, 516로·평화로 같은 긴 도로명만 반복됐습니다. 내부 코드와 링크 번호도 현장 담당자가 읽어야 하는 정보처럼 화면에 남아 있었습니다.

그래서 이번에는 기능을 늘리는 대신 “지금 어디를 먼저 보고, 누가 출발하며, 무엇을 확인한 뒤 승인해야 하는가”가 먼저 보이도록 화면과 운영 로직을 다시 만들었습니다.

[지도를 업무 언어로 바꿨습니다]

OpenStreetMap 배경 위에 RoadOps 분석 결과를 별도 계층으로 올렸습니다.

• 점검 우선순위: 먼저·주의·일반 표식
• 팀 이동 경로: 팀 고유색 점선
• 출발지: 집 아이콘과 시설명
• 점검 순서: 팀 색 테두리의 1·2·3 원
• 위치: 도로명과 함께 읍·면·동·리 인근 지역 표시

위험도와 팀 이동을 모두 굵은 색 선으로 표현하지 않았습니다. 같은 색이 같은 의미만 갖도록 시각 문법을 분리했습니다.

[임의 출발지를 공개자료 기반 거점으로 바꿨습니다]

제주도의회 공개자료를 바탕으로 데모의 동부·북부·서부팀 출발 후보를 교래 장비고, 용담 제설전진기지, 노형 장비고로 교체했습니다.

출발지가 바뀌자 2시간 안에 배정되는 업무는 기존 9개에서 6개로 줄었습니다. 안전 우선안의 위험가중 커버리지는 77.5%, 총 이동시간은 120.2분, 최대 팀 총소요는 117.9분이었습니다. 제약 위반은 0건입니다.

숫자는 낮아졌지만 결과는 더 정직해졌습니다. 임의 좌표가 만들던 낙관적인 배분을 버리고, 시간 안에 수행할 수 없는 업무 3개를 미배정으로 남겼습니다.

다만 공개자료에서 시설 주소를 확인한 것이지 실제 순찰팀의 현재 출동 규칙까지 확인한 것은 아닙니다. 화면에도 ‘공개자료 기반 출발 거점’으로 표시하고 운영 전 기관 확인이 필요하다는 한계를 남겼습니다.

[담당자가 우선순위를 바꾸면 바로 다시 계산합니다]

현장에는 점수보다 담당자가 먼저 아는 정보가 있습니다. 반복 민원, 행사, 공사 일정, 주민 제보 같은 정보입니다.

담당자는 자동 제안을 유지하거나 ‘가장 먼저·주의해서·일반 순서’로 직접 바꿀 수 있습니다. 조정 이유를 입력해야 하며, 변경 즉시 팀 배분을 다시 계산합니다. 처리 기록에는 내부 코드 대신 “확인 순서 조정”, “현재 사용자”, “왜 바꿨는지”가 한국어로 남습니다.

도로 통제와 폭우도 코드명이나 링크 번호로 설명하지 않습니다. “폭우가 예상되는 도로의 위험도와 점검·이동시간을 여유 있게 조정했고, 영향받은 팀의 남은 일정만 다시 계산했다”처럼 행동의 의미를 먼저 보여줍니다.

[기존 제주 시스템과 RoadOps의 역할을 구분했습니다]

제주는 관용차량 AI 카메라와 제설차량 복합 센서로 포트홀·도로 파손·결빙 위험을 탐지하는 통합 플랫폼을 구축 중입니다.

RoadOps의 목표는 이 시스템을 대체하는 것이 아닙니다. 탐지 결과 위에 다음 운영 의사결정 계층을 더하는 것입니다.

• 사고다발지역
• 반복 민원지역
• 비슷한 과거 날씨·환경에서 사건이 반복된 지역
• 공개된 비식별 생활안전 통계
• 관리기관·승인권자·경찰·소방 협조 상태
• 가용 인력·차량과 순찰 경로
• 통제·폭우 발생 시 부분 재계획과 처리 기록

범죄 정보는 도로보수 위험점수에 그대로 더하지 않습니다. 공개 격자나 행정구역 단위의 통계만 별도 ‘생활안전 협조 신호’로 사용해 야간 순찰 주의나 경찰 협조가 필요한 경우를 알리는 방향으로 설계할 계획입니다.

[AI를 어떻게 활용했나]

AI에게 화면을 예쁘게 만들어 달라고만 하지 않았습니다. 사용자가 이해하지 못한 표현, 지도에서 겹치는 정보, 설명할 수 없는 출발지와 지나치게 기술적인 기록을 하나씩 문제로 정의했습니다. 이후 공식자료 조사, 좌표·도로망 재계산, React 화면과 JavaScript 운영정책, Python 재계획 로직을 수정하고 실제 브라우저에서 직접 눌러 검증했습니다.

우선순위, 팀 배분, 경로, 영향팀 판정과 승인 가능 여부는 결정적인 코드가 계산합니다. LLM은 문제를 분해하고 구현·검증을 돕고, 검증된 결과를 현장 언어로 바꾸는 역할을 맡았습니다.

[현재까지 구현한 범위]

• 실제 배경지도와 확대·축소
• 우선순위·팀 경로·출발지·점검 순서 분리
• 공개자료 기반 도로관리 거점 3곳
• 담당자 우선순위 조정·사유·자동 재배분
• 통제·폭우 발생 시 영향팀 부분 재계획
• 한국어 처리 기록과 책임자 승인 흐름
• JavaScript 7개·Python 표적 26개 테스트 통과

아직 실제 운영 서비스는 아닙니다. 도로 위험은 저장된 스냅샷이고 이동시간은 실시간 ETA가 아닙니다. 표시한 지역은 좌표에서 찾은 인근 지명이지 확정 지번이 아닙니다. 사고다발·민원·유사기상 사건·생활안전 데이터도 이번에는 목표와 사용 원칙만 확정했으며 실제 결합은 다음 작업입니다.

[최종 목표]

목표는 위험 정보를 많이 보여주는 상황판이 아닙니다. 제주가 구축 중인 탐지·스마트 제설 시스템 위에 행정의 실제 질문을 연결하는 것입니다.

어디를 먼저 확인할지, 어느 기관과 팀이 움직일지, 무엇을 보존한 채 다시 계획할지, 누가 어떤 근거로 확정했는지까지 이어지는 제주 통합 도로안전 관제 Agent를 만들고 있습니다.

현장 담당자라면 위험을 발견한 뒤 가장 먼저 결정해야 하는 것은 무엇인가요?
