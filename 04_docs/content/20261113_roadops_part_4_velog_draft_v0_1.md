### **요약 & 나만의 인사이트**

그래서 팀·차량 자원 모델, 제주 방향성 도로망, 통제 링크, 근무시간을 하나의 최적화 문제로 다시 만들었다. 최종적으로 15,755개 실행 가능한 조합을 비교해 `안전 우선`과 `업무 균형` 두 대안을 만들었다. 두 대안 모두 9개 작업을 전부 배정하면서 근무시간 위반을 0건으로 줄였다.

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- 팀·차량·인원·출발지·근무시간·장비를 검증하는 자원 입력 모델 구현
- 같은 도로의 여러 이벤트를 하나의 현장 작업으로 통합
- 위험순·최근접 기준선 배분 구현
- 제주 방향성 노드·링크망 기반 이동시간 행렬 생성
- 고정·필수·장비·근무시간을 지키는 제약 기반 최적화 구현
- 안전 우선·업무 균형 두 대안과 미배정 사유 출력

**문제 상황**

- 현재 시점에서 점수를 받은 이벤트 14건 중 같은 `link_id`에 여러 이벤트가 있었다. 이벤트 행마다 출동시키면 같은 도로에 순찰팀이 중복 배정될 수 있었다.
- 직선거리와 고정속도로 계산한 이동시간은 도로 연결, 진행 방향, 우회로를 반영하지 못했다.
- 위험순 기준선과 최근접 기준선은 모두 9개 작업을 배정했지만, 실제 도로시간에서도 근무시간을 지키는지는 확인하지 못했다.
- 고정 업무나 필수 업무를 점수 때문에 다른 팀으로 넘기거나 미배정해서는 안 됐다.
- 최적화가 답을 만들더라도 왜 그 팀이 그 순서로 가는지 다시 확인할 수 있어야 했다.

**시도한 방법 & 탐색 과정**

- **먼저 배분 단위를 이벤트가 아니라 도로 작업으로 바꿨다.**

현재 시간지평의 위험예보는 22행이었다. 이 중 점수와 순위가 유효한 행은 14개였고, 같은 링크의 이벤트를 합치자 10개 현장 작업이 됐다. 운영자가 제외한 링크 1개를 빼고 최종 배분 후보는 9개였다.

```text
현재 위험예보 22행
  → 점수·순위 유효 이벤트 14행
  → 동일 link_id 통합
  → 고유 현장 작업 10개
  → 운영자 제외 1개
  → 배분 후보 9개
```

같은 링크를 합칠 때는 최고 위험점수를 대표점수로 사용하고, 원본 `event_id`, 원천, 이벤트 종류와 건수는 모두 보존했다. 중복 출동은 막되 근거를 버리지는 않았다.

- **자원 입력부터 실패할 수 있게 만들었다.**

예시 시나리오는 순찰팀 3개, 차량 3대, 팀당 2명, 근무시간 2시간이다. 입력 단계에서 다음 조건을 검사했다.

1. 같은 차량이 두 팀에 배정됐는가?
2. 차량 정원보다 인원이 많은가?
3. 계획 시작시각이 팀 근무시간 밖인가?
4. 필수 링크와 제외 링크가 겹치는가?
5. 고정 업무의 팀과 링크가 실제로 존재하는가?
6. 현장에 필요한 기술과 장비를 팀이 가지고 있는가?

배정 알고리즘이 잘 작동해도 입력 자원이 모순이면 결과는 의미가 없다. 그래서 자원 오류를 자동 보정하지 않고 계획 생성 전에 실패하도록 했다.

- **두 개의 단순 기준선을 먼저 만들었다.**

`risk_first`는 필수 작업을 먼저 반영한 뒤 위험점수 내림차순으로 작업을 고르고, 가장 가까운 실행 가능 팀에 배정한다.

`nearest`는 필수 작업을 먼저 반영하되 이후에는 전체 팀–작업 조합 중 가장 가까운 쌍부터 선택한다.

처음에는 두 기준선 모두 좋아 보였다.

| 지표 | 위험순 | 최근접 |
|---|---:|---:|
| 배정 작업 | 9 / 9 | 9 / 9 |
| 위험가중 커버리지 | 100% | 100% |
| 직선거리 추정 이동시간 | 118.103분 | 107.818분 |
| 최대 팀 총소요시간 | 92.051분 | 101.828분 |
| 직선거리 기준 제약 위반 | 0건 | 0건 |

표만 보면 최근접 방식이 더 효율적이었다. 총이동시간도 짧고 모든 작업을 배정했다. 문제는 이 숫자가 실제 도로가 아니라 위경도 직선거리와 시속 40km 가정에서 나온 값이라는 점이었다.

- **제주 도로망으로 같은 계획을 다시 검사했다.**

국토교통부 전국표준 노드링크에서 추출한 제주 방향성 노드 27,656개와 링크 37,087개를 사용했다. 각 링크의 형상 길이와 제한속도로 자유흐름 이동시간을 계산하고, 팀→현장과 현장→현장 108개 경로를 만들었다.

```text
팀 출발점 3개 + 현장 출발점 9개
  × 도착 현장 9개
  = 이동경로 108개
```

여기서 사용하는 시간은 실시간 교통 ETA가 아니다. 제한속도 기반 `free_flow_speed_limit_estimate`다. 그래도 직선거리와 달리 도로의 방향과 연결구조는 반영한다.

같은 방문 순서를 도로망 시간으로 다시 계산하자 결과가 뒤집혔다.

**최종 해결 및 적용 코드**

현장 9개 규모에서는 근사값보다 가능한 순서를 직접 비교하는 편이 검증하기 쉬웠다. 팀별로 근무시간 안에 가능한 방문 순서를 먼저 만들고, 팀끼리 작업이 겹치지 않는 조합을 완전탐색했다.

```python
# 제약 기반 배분 v0.1 개념 요약

HARD_CONSTRAINTS = [
    "한 작업은 한 팀에만 배정",
    "필수 작업은 반드시 배정",
    "고정 업무는 지정 팀에 배정",
    "기술·장비 요구조건 충족",
    "팀별 최대 작업 수 준수",
    "도로 이동 + 점검시간 <= 근무시간",
    "통제·단절 경로 사용 금지",
]

# 1. 팀별 실행 가능한 방문 순서 열거
team_route_options = enumerate_feasible_routes(
    travel_time_matrix,
    service_minutes,
    shift_minutes,
)

# 2. 작업이 겹치지 않는 팀 경로 조합 생성
candidates = combine_without_duplicate_tasks(team_route_options)

# 3. 목적에 따라 두 대안 선택
safety_first = maximize_risk_then_minimize_travel(candidates)
balanced = minimize_max_team_time(
    candidates,
    minimum_risk=safety_first.risk_score * 0.95,

```

`안전 우선`은 위험가중 커버리지를 먼저 최대화하고, 같은 커버리지에서는 총 도로 이동시간이 짧은 계획을 선택한다.

`업무 균형`은 안전 우선안 위험점수의 최소 95%를 지키는 후보만 남긴 뒤, 팀 최대 소요시간과 팀별 소요시간 분산을 줄인다.

어느 안이 무조건 정답이라고 말할 수는 없다. 이동시간을 최소화할지, 팀 간 부담을 고르게 할지는 담당자가 상황에 따라 선택해야 한다. RoadOps의 역할은 하나의 답을 강요하는 것이 아니라 **제약을 모두 지킨 대안과 그 차이를 설명하는 것**이다.

**개발 중 발견한 실패 사례**

- **직선거리의 가짜 안정성:** 직선거리 기준에서는 두 계획 모두 근무시간 위반이 없었다. 도로망으로 바꾸자 각각 1개 팀이 10분 이상 초과했다. 앞으로 운영 가능성 판정에는 직선거리 시간을 사용하지 않는다.
- **통제 링크의 단절:** 실제 링크 하나를 통제로 제거한 시험에서 108개 경로 중 19개가 `unavailable`이 됐다. 우회로가 없을 때 직선거리로 대체하지 않고 경로 없음으로 남겼다. 통제 링크를 실제로 통과한 경로는 0건이었다.
- **필수 작업의 강제 완화:** 필수 작업으로 가는 경로를 모두 끊은 테스트에서는 낮은 점수 계획을 대신 만들지 않고 `no_globally_feasible_plan`으로 실패했다.
- **탐색 규모 문제:** 현재 완전탐색은 최대 현장 10개까지만 허용한다. 그 이상에서는 느린 답을 내거나 임의로 잘라내지 않고 확장형 최적화 엔진이 필요하다고 명시한다.

전체 자동화 테스트는 124개가 통과했다. 동일한 자원·위험 작업·도로망 행렬을 넣으면 같은 팀, 같은 방문 순서, 같은 미배정 사유가 나오도록 동률 해소 규칙도 고정했다.

### **배운 점 / 재발 방지 노트**

- **거리보다 경로가 먼저다:** 두 지점의 직선거리가 짧아도 도로 방향과 연결구조 때문에 이동시간은 길어질 수 있다. 직선거리는 화면용 참고값이지 근무시간 제약의 근거가 아니다.
- **목적함수보다 하드 제약이 먼저다:** 필수·고정·장비·근무시간은 점수로 거래하면 안 된다. 지킬 수 없으면 낮은 품질의 답을 만드는 대신 실패해야 한다.
- **중복 이벤트와 중복 업무는 다르다:** 한 도로에 이벤트가 여러 개 있다고 여러 번 출동할 필요는 없다. 배분 전 작업 단위를 먼저 정규화해야 한다.
- **최적이라는 말에는 기준이 필요하다:** 안전 우선은 이동시간이 짧았고, 균형안은 팀 부담 분산이 낮았다. 무엇을 최적화했는지 없이 “최적안”이라고 부르면 안 된다.

### **새롭게 알게 된 점**

**1. 기준선은 약해야 하는 비교 대상이 아니었다**

- 위험순과 최근접 기준선은 최적화안의 성능을 돋보이게 하기 위한 장식이 아니다.
- 같은 입력과 같은 도로시간으로 다시 평가해야 어디에서 실패했는지 설명할 수 있다.
- 이번에는 두 기준선이 위험 커버리지는 100%였지만 근무시간 제약에서 실패했다.

**2. 업무 균형은 작업 개수만 같다고 해결되지 않았다**

- 두 최적화안 모두 팀당 작업은 3개였다.
- 하지만 도로 이동과 점검시간을 합치면 팀별 부담 차이는 크게 달랐다.
- 업무량은 작업 건수뿐 아니라 총소요시간과 분산으로 같이 봐야 했다.

**3. 경로 실패도 결과 데이터였다**

- 통제로 갈 수 없는 현장은 0분이나 매우 큰 임의 숫자로 바꾸지 않았다.
- `unavailable`과 원인을 별도로 남기면 최적화기가 해당 경로를 사용하지 않고, 화면에서도 왜 미배정됐는지 설명할 수 있다.
- 실패를 숨기지 않는 것이 오히려 Agent의 행동을 더 예측 가능하게 만들었다.

### **학습 중 어려웠던 부분**

**안전 우선과 효율의 순서 정하기**

- 위험점수와 이동시간을 하나의 가중합으로 만들면 가중치에 따라 필수에 가까운 고위험 작업이 빠질 수 있었다.
- 그래서 먼저 하드 제약을 적용하고, 안전 우선에서는 위험 커버리지를 사전식으로 최대화했다.
- 업무 균형안도 안전 우선 점수의 95% 아래로 떨어지지 않도록 별도 기준을 뒀다.

**실시간 ETA처럼 보이지 않게 표현하기**

- 도로망 경로를 계산하면 숫자가 정교해 보여서 실제 교통시간처럼 오해하기 쉽다.
- 현재 값은 링크 제한속도 기반 자유흐름 추정치다. ITS 혼잡과 회전제한은 아직 반영하지 않았다.
- 결과 필드와 문서에 이 한계를 반복해서 표시했다.

**완전탐색의 범위 제한**

- 현장 9개는 모든 실행 가능한 조합을 비교할 수 있었지만 현장이 늘어나면 조합 수가 급격히 커진다.
- 현재는 최대 10개까지만 허용하고, 그 이상은 OR-Tools 같은 확장형 엔진으로 넘길 계획이다.
- 작은 데모에서 정확히 검증하는 것과 실제 규모에서 빠르게 푸는 것은 다른 문제였다.

### **AI를 어떻게 활용했나**

AI는 최적 배치를 감으로 고르지 않았다. 대화로 자원 모델과 하드 제약을 정리하고, 위험순·최근접 기준선이 왜 필요한지 설계했다. 이후 도로망 경로 계산, 완전탐색, 제약 재검증 코드를 구현하고 실패 사례를 테스트로 고정하는 데 활용했다.

최종 팀·작업 조합은 Python 코드가 15,755개 후보를 같은 규칙으로 비교해 선택한다. LLM은 다음 단계에서 사용자의 요청을 해석하고 두 대안의 차이를 설명하는 역할을 맡는다. 위험점수, 이동시간, 제약 판정과 최적화 결과를 LLM의 문장 생성에 맡기지는 않는다.

**Agent 도구 흐름 연결**

- “팀 3개, 차량 3대, 2시간 안에 순찰계획을 만들어줘”라는 요청을 구조화한다.

- 각 단계의 입력·출력·실패 이유를 감사 로그에 남긴다.

**돌발상황 부분 재계획**

- 폭우나 도로통제를 주입한 뒤 영향받은 경로만 다시 계산한다.
- 이미 완료한 업무와 담당자가 고정한 업무는 유지한다.
- 변경된 팀, 빠진 현장, 이동시간과 커버리지 차이를 전후 비교한다.

**제주 도로 지도 웹사이트**

- 위험 링크, 팀 출발지, 방문 순서와 실제 경로를 지도에 표시한다.
- 안전 우선·업무 균형 대안을 한 화면에서 비교한다.
- 담당자가 한 업무를 고정하거나 제외한 뒤 재계획할 수 있게 한다.
