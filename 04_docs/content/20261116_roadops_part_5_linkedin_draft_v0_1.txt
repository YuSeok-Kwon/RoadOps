AI와 함께 제주 도로위험 순찰배치 Agent를 만들고 있습니다 — RoadOps 5부

“지도에서 팀과 현장을 바꾸고 승인 버튼을 누르면 실제 계획이 될까?”

이번에는 RoadOps를 위험과 경로를 보여주는 지도에서 자원 확인, 업무 수정, 안전 재검증, 담당자 승인과 감사 로그까지 이어지는 웹 MVP로 확장했습니다.

화면을 만드는 것보다 더 어려운 문제는 ‘언제 승인을 막아야 하는가’였습니다.

[수정했다고 재계산된 것은 아닙니다]

현재 웹에서는 검증이 완료된 안전 우선과 균형 운영 두 계획을 비교할 수 있습니다. 팀·차량·인원·근무시간과 현장별 담당팀·고정·제외 조건도 확인하고 수정할 수 있습니다.

하지만 인원이나 담당팀을 바꾸면 기존 경로를 수정된 계획처럼 보여주지 않습니다. 경로를 숨기고 ‘백엔드 재계획 필요’로 전환하며 승인을 차단합니다.

입력을 바꾸는 것과 그 조건으로 다시 계산했다는 것은 다른 상태이기 때문입니다.

[승인 대상을 계획 지문으로 남깁니다]

승인 전에는 데이터 품질, 이동시간의 의미, 현장 재확인을 모두 체크해야 합니다. 제약 오류가 0건이고, 안전확인 3개와 담당자·승인 사유가 모두 있어야 승인이 가능합니다.

승인 기록에는 자원, 업무, 배분안과 What-if 조건으로 만든 계획 지문이 함께 남습니다. 승인 후 입력이 바뀌면 예전 승인은 이력으로 보존하되 현재 계획의 승인으로 표시하지 않습니다.

[장애가 나면 더 보수적으로 전환합니다]

실시간 API 실패, 오래된 데이터, 잘못된 도로 링크, 실행 가능한 배분안 부재, 설명 생성 실패를 포함한 6개 장애를 인위적으로 주입했습니다.

• 사용 가능한 최근 캐시: 출처·나이를 표시하고 제한적 재생
• 캐시 없음·스냅샷 기한 초과: 순위·배분 보류
• 참조망에 없는 링크: 제외하되 원본·사유 보존
• 최적화 불능: 하드 제약을 풀지 않고 수동 개입
• 설명 생성 실패: 검증된 Tool 결과만 결정적 템플릿으로 전환

6개 시나리오의 53개 안전 검사는 모두 통과했고, Python 전체 자동화 테스트는 152개가 통과했습니다. 어떤 시나리오에서도 실패값을 0으로 바꾸거나 자동 출동을 허용하지 않았습니다.

[AI를 어떻게 활용했나]

AI는 누구를 어디로 보낼지나 승인해도 되는지를 느낌으로 판단하지 않았습니다. 대화로 사용자의 검토 순서, 수정 후 무효화할 상태, 장애별 안전 전환을 분해했습니다. 이후 React 운영 화면과 JavaScript 제약 검증, Python 장애 주입 평가를 구현하고 실패 사례를 테스트로 고정했습니다.

승인 가능 여부, 계획 지문, 장애 복구 상태는 결정적인 JavaScript·Python 규칙이 계산합니다. LLM은 향후 사용자의 다양한 요청을 구조화하고 검증된 Tool 결과를 설명하는 역할로 추가할 계획입니다.

[현재까지 구현한 범위]

• 제주 도로의 현재·1·3·6시간 위험과 팀 경로 지도
• 자원·현장 업무 편집과 제약 재검증
• 안전 우선·균형 운영 계획 비교
• 안전확인 3개·담당자·사유를 갖춘 승인 흐름
• 계획 지문과 브라우저 감사 로그
• 수정 후 미계산 경로 승인 차단
• 6개 장애·복구 안전 정책 검증

아직 실제 운영 서비스는 아닙니다. 승인·감사 로그는 현재 브라우저에만 저장되고, 수정 후 재최적화는 웹 API와 연결되지 않았습니다. 위험 데이터도 저장 스냅샷이며 이동시간은 실시간 ETA가 아닙니다. 장애 평가 역시 실서버 장애가 아닌 통제된 시뮬레이션입니다.

[최종 목표]

목표는 AI가 현장 지시를 대신 내리는 것이 아닙니다. 담당자가 가용 자원과 데이터의 한계를 함께 보고, 실행 가능한 대안을 비교한 뒤, 자신이 확인한 계획만 승인할 수 있는 의사결정 환경을 만드는 것입니다.

여러분이 현장 담당자라면 승인 전에 반드시 확인하고 싶은 정보는 무엇인가요?
