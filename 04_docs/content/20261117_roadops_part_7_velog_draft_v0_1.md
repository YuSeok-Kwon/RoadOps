# [2026-11-17] 제주 RoadOps 프로젝트 7부 — 탐지 시스템 위에 ‘실행’을 연결하는 통합 도로관제 Agent

### **요약 & 나만의 인사이트**

지난 작업에서 RoadOps는 위험 도로와 순찰 경로를 보여주고, 담당자가 자원과 업무를 확인한 뒤 계획을 승인하는 웹 MVP까지 발전했다. 화면이 생기니 이제 정말 쓸 만해 보였다. 그런데 직접 데모를 해보자 문제가 바로 보였다.

지도에서 색 선은 많은데 무엇이 위험 도로이고 무엇이 팀 이동 경로인지 구분하기 어려웠다. 출발지는 왜 그 위치인지 설명할 수 없었고, 도로명만 반복돼 실제로 어디를 점검해야 하는지 알기 힘들었다. `spatial_fallback`, `road_closure`, 링크 번호 같은 내부 용어도 현장 담당자에게 그대로 노출됐다. ~~개발자인 내가 다시 봐도 한 번에 이해하지 못했다.~~

그래서 이번에는 기능을 더 넣기 전에 화면의 질문을 바꿨다.

> “이 데이터가 어떻게 계산됐는가?”보다 “지금 어디를 먼저 보고, 누가 출발하며, 무엇을 확인한 뒤 승인해야 하는가?”가 먼저 보여야 한다.

제주가 현재 구축 중인 AI 도로안전·스마트 제설 플랫폼도 다시 조사했다. 관용차량 카메라와 복합 센서로 포트홀·도로 파손·결빙 위험을 탐지하고 제설 판단을 지원하는 체계다. 그렇다면 RoadOps가 같은 탐지 화면을 하나 더 만드는 것은 차별점이 약했다.

RoadOps의 역할을 **탐지 이후의 운영 의사결정 계층**으로 다시 정의했다. 기존 시스템이 “무슨 위험이 어디서 발견됐는가”를 알려준다면, RoadOps는 사고다발·반복 민원·유사 기상 이력까지 함께 보며 “어디를 먼저 확인하고, 어느 기관과 팀이 어떤 순서로 움직이며, 상황이 바뀌면 무엇만 다시 계획할 것인가”를 연결한다.

이번 작업에서 가장 크게 배운 점은 **통합 관제는 데이터를 한 화면에 많이 모으는 일이 아니라, 서로 다른 위험을 행정의 다음 행동으로 연결하는 일**이라는 것이다.

### **프로젝트: 제주 통합 도로안전 관제 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- 제주 실지도를 사용하는 확대·축소 가능한 도로 관제 화면
- 위험 우선순위와 팀 이동 경로를 서로 다른 시각 문법으로 분리
- 순찰 출발지를 임의 좌표에서 공개자료 기반 도로관리 거점으로 교체
- 도로명 대신 읍·면·동과 인근 지역을 함께 표시
- 담당자가 도로 확인 순서를 직접 조정하고 사유를 남기는 흐름
- 입력 변경 즉시 팀 배분을 다시 계산하는 운영 로직
- 배분 대안·통제·폭우 시나리오 설명과 처리 기록의 한국어화
- 기존 제주 도로안전 플랫폼과 RoadOps의 역할 구분
- 사고다발·상습민원·유사기상 사건·생활안전 신호를 포함한 통합 관제 목표 확정

**문제 상황**

- 기존 지도는 자체 도로선만 그려 확대해도 주변 지명과 세부 도로가 늘어나지 않았다.
- 빨강·주황·파랑 위험선과 팀별 경로선이 겹쳐 같은 색이 서로 다른 의미를 가졌다.
- 숫자 1·2·3은 순찰 순서였지만 테두리 색이 팀과 연결되지 않아 어느 팀의 순서인지 바로 알기 어려웠다.
- 팀 출발지는 데모용 임의 좌표라 실제 행정 운영의 근거로 설명할 수 없었다.
- `516로`, `평화로`처럼 긴 도로명만 반복돼 구체적인 점검 위치를 찾기 어려웠다.
- 담당자가 현장 민원이나 행사 정보를 알고 있어도 시스템이 제안한 순서를 직접 바꿀 수 없었다.
- 영어 코드와 링크 번호는 개발에는 유용하지만 공무원의 판단에는 불필요한 인지 부담이었다.
- 이미 제주가 AI 도로 통합관제 플랫폼을 구축 중이어서, RoadOps가 무엇을 추가하는지 더 명확히 해야 했다.

**시도한 방법 & 탐색 과정**

- **지도에 실제 배경을 넣되, 분석 정보와 역할을 섞지 않았다.**

OpenStreetMap 타일을 Web Mercator 좌표계로 투영하고 현재 화면에 보이는 타일만 불러오게 했다. 마우스 휠이나 `+/-` 버튼으로 확대하면 타일 단계도 함께 올라가 주변 도로와 지명이 더 자세히 보인다.

그 위에 RoadOps 분석 결과를 별도 계층으로 올렸다.

```text
배경지도       : 실제 도로·지명·지형을 읽는 기준
점검 우선순위  : 도로 위 작은 ‘먼저·주의·일반’ 표식
팀 이동 경로   : 팀 고유색 점선
팀 출발지      : 집 모양 아이콘
점검 순서      : 팀 색 테두리를 가진 1·2·3 원
재계획 비교    : 변경 전·후 경로만 별도 표현
```

이전처럼 위험도와 팀 경로를 모두 굵은 색 선으로 표현하지 않았다. 위험은 **업무 우선순위 표식**, 이동은 **팀 경로선**으로 분리했다. 색을 더 많이 쓰는 대신 같은 색이 같은 의미만 갖게 했다.

- **출발지는 ‘제주도 어딘가’가 아니라 공개자료로 설명할 수 있는 거점으로 바꿨다.**

제주도의회 공개자료에서 도로관리과가 관리하는 장비고와 제설전진기지를 확인했다. 데모의 동부·북부·서부팀 출발 후보를 다음처럼 교체했다.

| 팀 | 공개자료 기반 출발 후보 | 화면 표시 |
|---|---|---|
| 동부팀 | 교래 장비고 | 집 아이콘 + 교래 장비고 |
| 북부팀 | 용담 제설전진기지 | 집 아이콘 + 용담 제설전진기지 |
| 서부팀 | 노형 장비고 | 집 아이콘 + 노형 장비고 |

여기서 중요한 한계도 남겼다. 시설의 존재와 주소는 공개자료로 확인했지만, 현재 실제 순찰팀이 매일 이곳에서 출동한다는 운영 절차까지 확인한 것은 아니다. 따라서 화면에는 `공개자료 기반 출발 거점`으로 표시하고, 실제 운영 전에는 도로관리과의 현재 배치와 출동 규칙을 확인해야 한다.

- **도로명을 위치로 착각하지 않도록 인근 지역을 함께 표시했다.**

기존에는 목록과 경로 상세에 `516로`, `평화로`가 반복됐다. 같은 도로가 길게 이어지므로 현장 위치를 판단하기 어려웠다. 도로 링크 좌표를 기준으로 가까운 읍·면·동과 리 단위 지역을 찾아 다음처럼 표시했다.

```text
기존: 516로
변경: 서귀포시 남원읍 신례리 · 516로 인근

기존: 평화로
변경: 제주시 애월읍 광령리 · 평화로 인근
```

다만 이것은 확정 지번이 아니다. 현재 화면은 좌표에서 찾은 **인근 지역명**이며, 정확한 지번·도로명주소는 VWorld·Kakao Local·주소정보 API 같은 역지오코딩 서비스를 연결한 뒤 별도로 검증해야 한다. 보기 좋게 만들기 위해 근거보다 정밀한 주소를 만들어내지는 않았다.

- **AI 제안과 담당자 판단을 경쟁시키지 않고 하나의 기록으로 연결했다.**

위험점수만으로 알 수 없는 현장 정보가 있다. 반복 민원, 행사, 공사 일정, 주민 제보처럼 담당자가 더 빨리 아는 정보다. 그래서 `자동 제안 유지`, `가장 먼저`, `주의해서`, `일반 순서` 중 하나를 직접 선택할 수 있게 했다.

담당자가 순서를 바꾸면 조정 이유를 5자 이상 입력해야 한다. 이유가 없으면 최종 확인 단계에서 검증 오류가 발생한다. 변경 즉시 팀 배분도 다시 계산하고 처리 기록에 한국어로 남긴다.

```javascript
const effectivePriority = manualPriority ?? suggestedPriority;

if (manualPriority && priorityReason.trim().length < 5) {
  blockApproval("담당자 조정 이유가 필요합니다.");
}

recalculateTeamAssignments(effectivePriority);
appendAuditLog({
  action: "확인 순서 조정",
  details: "516로의 확인 순서를 '가장 먼저' 단계로 바꾸고 팀 배분을 다시 계산했습니다.",
});
```

처음 구현한 승인 웹에서는 조건을 바꾸면 `재계산 필요`라고 멈췄다. 이번에는 브라우저 안에서 실행 가능한 범위의 배분을 즉시 다시 계산한다. 사용자는 다시 계산 버튼을 찾을 필요가 없다. 단, 이 계산은 현재 저장된 경로 후보 안에서의 팀 재배분이며, 새로운 도로망 최단경로까지 서버에서 다시 만드는 완전한 재최적화는 아니다.

- **내부 코드는 숨기고 행동의 의미를 보여줬다.**

화면에서 다음 표현을 바꿨다.

| 내부 표현 | 운영 화면 표현 |
|---|---|
| `road_closure` | 도로 통제 가정 |
| `heavy_rain What-if` | 폭우 가정 |
| `priority_changed` | 확인 순서 조정 |
| `local-operator` | 현재 사용자 |
| 영향 링크 번호 나열 | 폭우가 예상되는 도로의 점검·이동시간을 여유 있게 조정 |

링크 번호와 내부 상태값은 감사·디버깅 데이터에는 남길 수 있지만, 첫 화면에서 담당자에게 읽도록 요구하지 않는다. 화면에는 “누가, 무엇을, 왜 다시 확인해야 하는가”만 먼저 보여준다.

- **기존 제주 시스템과 경쟁하지 않는 목표로 다시 정의했다.**

제주는 2026년 말까지 관용차량의 AI 카메라와 제설차량 복합 센서로 포트홀·도로 파손·결빙 위험을 탐지하는 통합 플랫폼을 구축하고 있다. 이 체계는 위험을 더 빠르게 발견하는 데 강점이 있다.

RoadOps는 그 위에 다음 의사결정 계층을 추가하는 방향으로 목표를 바꿨다.

```text
기존 플랫폼
  위험 탐지 → 결빙 예측 → 현장 알림 → 제설 상태 확인

RoadOps
  탐지 결과 수신
  + 사고다발지역
  + 반복 민원지역
  + 유사한 과거 날씨·환경의 사건지역
  + 공개 생활안전 통계
  → 확인 우선순위
  → 관리기관·승인권자 확인
  → 가용팀·차량 배분
  → 순찰 경로·부분 재계획
  → 경찰·소방 협조 및 처리 기록
```

범죄 정보는 도로보수 점수에 그대로 더하지 않는다. 공개된 격자나 행정구역 단위의 비식별 통계만 `생활안전 협조 신호`로 분리해, 야간 순찰 주의나 경찰 협조가 필요한 상황을 알리는 보조 근거로 사용할 계획이다. 개인 사건 위치나 신고 원문을 도로관리 화면에 노출하는 방식은 제외한다.

**최종 해결 및 적용 코드**

지도와 운영 상태의 핵심 구조는 다음처럼 정리했다.

```text
관제 화면 상단
  현재/1/3/6시간 + 안전 우선/균형 운영 + 통제/폭우 가정 + 테마

핵심 상황
  점검 대상 + 먼저 확인 + 배분 완료 + 제약 위반

지도
  실제 배경지도 + 우선순위 표식 + 팀 경로 + 공개자료 기반 출발 거점

운영 패널
  우선순위 목록 → 선택 구간 상세 → 출동계획

출동계획
  출동팀 → 도로·우선순위 → 확인·확정 → 처리 기록
```

지도는 `보이는 도로가 많다`보다 `다음 행동을 찾기 쉽다`를 우선했다. 화면 상단의 주요 수치는 네 개로 줄였고, 데이터 근거 반영률과 품질 플래그는 선택 구간의 하단 상세로 내렸다. 지도 읽는 방법도 항상 공간을 차지하지 않고 펼침형 도움말로 바꿨다.

**실제 검증 결과**

공개자료 기반 출발 거점으로 도로망 이동시간과 배분을 다시 계산했다. 출발지가 바뀌면서 이전 결과와 같은 숫자가 나오지 않았다. 오히려 이것이 정상이다. 임의 좌표를 공식 후보 거점으로 바꿨는데 이동시간이 그대로라면 계산을 의심해야 한다.

| 항목 | 결과 |
|---|---:|
| 출동팀 | 3개 |
| 점검 업무 | 10개 |
| 배분 대상 | 9개 |
| 2시간 제약 내 배분 | 6개 |
| 미배정 | 3개 |
| 안전 우선 위험가중 커버리지 | 77.5% |
| 안전 우선 총 이동시간 | 120.2분 |
| 최대 팀 총소요 | 117.9분 |
| 제약 위반 | 0건 |

이전 데모는 9개 업무를 모두 배정했지만, 실제 후보 거점과 도로망 경로를 반영하자 2시간 안에 6개만 실행 가능했다. 숫자는 나빠졌지만 결과는 더 정직해졌다. 미배정 업무를 숨기거나 근무시간을 넘겨 억지로 채우지 않았다.

부분 재계획도 새 출발지와 배분안에 맞춰 다시 만들었다.

| 시나리오 | 영향팀 | 이동시간 변화 | 제약 위반 |
|---|---:|---:|---:|
| 도로 통제 가정 | 1개 팀 | +0.912분 | 0건 |
| 폭우 가정 | 1개 팀 | +6.483분 | 0건 |

JavaScript 운영 정책 테스트 7개와 Python 표적 테스트 26개가 통과했다. 대시보드 빌드와 실제 브라우저 화면에서도 다음을 직접 확인했다.

- 지도 확대 시 실제 지명과 도로가 상세화되는가
- 위험 우선순위와 팀 경로가 다른 표현으로 보이는가
- 출발지가 집 아이콘과 시설명으로 표시되는가
- 점검 순서 원의 테두리가 팀 색과 일치하는가
- 담당자 우선순위 변경 시 조정 이유 입력이 나타나는가
- 팀 배분이 즉시 다시 계산되는가
- 통제·폭우 설명에 내부 코드와 링크 번호가 노출되지 않는가
- 가로 스크롤 없이 화이트·다크 테마가 동작하는가

**개발 중 발견한 실패 사례**

- **공식 거점으로 바꾸자 기존 재계획 테스트가 실패했다:** 이전 배분안의 완료 업무가 새 배분안에는 없었다. 새 계획에 실제 포함된 첫 업무를 완료 상태로 다시 지정했다.
- **통제 링크가 새 경로를 지나지 않았다:** 기존 통제 링크는 출발지가 바뀐 뒤 어떤 팀에도 영향을 주지 않았다. 새 남은 경로가 실제 사용하는 링크를 통제 대상으로 바꾸고 영향팀 판정을 다시 검증했다.
- **더 현실적인 출발지가 더 낮은 배정률을 만들었다:** 9개 전부 배정에서 6개 배정으로 줄었다. 임의 좌표가 얼마나 낙관적인 결과를 만들 수 있는지 확인했다.
- **처리 기록에 영어가 남았다:** 화면 본문은 한국어였지만 감사 로그 작성자가 `local-operator`로 표시됐다. `현재 사용자`로 바꾸고 조정 이유도 별도 기록하도록 수정했다.
- **상세 주소를 너무 정밀하게 보일 위험:** 링크 좌표로 찾은 인근 지역을 지번처럼 보이면 안 됐다. 화면과 문서에 `인근`, `확정 지번 아님`이라는 경계를 남겼다.

### **배운 점 / 재발 방지 노트**

- **출발지는 최적화 입력이자 행정 근거다:** 지도에서 그럴듯한 위치보다 실제 거점 후보와 출처를 남겨야 한다.
- **현실적인 입력은 성능 숫자를 낮출 수 있다:** 배정률이 낮아져도 불가능한 계획을 가능한 것처럼 보이는 것보다 낫다.
- **색은 꾸미는 재료가 아니라 업무 문법이다:** 우선순위, 팀, 상태가 같은 색 체계를 공유하면 판단이 느려진다.
- **담당자 수정은 예외가 아니라 제품의 핵심 흐름이다:** AI 제안보다 현장 정보가 빠를 수 있으므로 수정·사유·재계산·기록을 하나로 묶어야 한다.
- **통합은 모든 점수를 더하는 것이 아니다:** 범죄, 민원, 사고, 도로위험은 목적과 권한이 다르다. 점수층·주의 신호·기관 인계를 분리해야 한다.

### **새롭게 알게 된 점**

**1. 기존 플랫폼의 강점을 인정해야 차별점이 보였다**

- 제주 시스템은 포트홀·도로 파손·결빙을 발견하고 제설 판단을 지원한다.
- RoadOps가 같은 탐지 기능을 다시 만드는 것은 비용도 크고 의미도 약하다.
- 탐지 결과를 관할·인력·차량·순찰 순서·승인으로 연결하는 운영 계층이 RoadOps의 역할이다.

**2. 사용성 검증은 글자 크기보다 질문 순서를 보는 일이었다**

- 담당자는 근거 반영률보다 먼저 갈 곳과 가용팀을 먼저 본다.
- 품질정보는 숨기면 안 되지만 첫 화면의 가장 큰 자리를 차지할 필요도 없다.
- 중요한 정보는 위로, 전문적인 근거와 한계는 선택한 도로의 상세로 내렸다.

**3. ‘실제 지도’는 디자인과 계산을 동시에 검증했다**

- 주변 지명과 도로를 보니 임의 출발지와 경로 중첩이 더 쉽게 드러났다.
- 확대해도 정보가 늘지 않는 자체 지도는 현장 위치 확인에 한계가 있었다.
- 지도 타일을 넣은 뒤에도 분석 표식은 별도 계층으로 유지해야 읽을 수 있었다.

### **학습 중 어려웠던 부분**

**정확한 위치와 공개자료의 경계**

- 공개문서에서 시설 주소는 확인할 수 있었지만 현재 출동팀의 실제 시작 위치까지 확인한 것은 아니다.
- 좌표도 주소 기반 변환값이므로 시설 출입구나 차량 출차 지점과 다를 수 있다.
- 데모에서는 출처와 정밀도를 함께 저장하고 운영기관 확인 전에는 확정값으로 부르지 않기로 했다.

**자동 재계산의 범위**

- 사용자는 입력을 바꾸면 결과도 즉시 바뀌길 기대한다.
- 브라우저에서는 현재 경로 후보 안에서 팀 배분을 다시 계산할 수 있지만 새로운 통제·회전제한을 반영한 도로망 탐색까지 수행하지 않는다.
- UI에서는 즉시 재배분과 서버 재최적화를 같은 것으로 표현하지 않도록 한계를 남겨야 했다.

**범죄·민원 데이터를 어디에 사용할지**

- 생활안전 신호를 모두 도로위험 점수에 더하면 도로관리 업무와 경찰 업무의 경계가 사라진다.
- 민원 건수는 인구와 이용량, 신고 접근성의 영향을 받으므로 단순 빈도로 위험을 단정할 수 없다.
- 다음 단계에서는 위험점수, 별도 주의 표식, 경찰·소방 인계 조건을 분리해 평가해야 한다.

### **AI를 어떻게 활용했나**

AI에게 화면을 예쁘게 만들어 달라고만 하지 않았다. 실제 사용자가 이해하지 못한 표현, 지도에서 겹치는 정보, 설명할 수 없는 출발지와 지나치게 기술적인 처리 기록을 하나씩 문제로 정의했다. 이후 공식 자료 조사, 좌표·도로망 재계산, React 지도와 운영 입력, 테스트 수정, 실제 브라우저 검증을 반복했다.

우선순위, 팀 배분, 경로, 영향팀 판정과 승인 가능 여부는 JavaScript·Python 규칙이 계산한다. LLM은 문제를 분해하고 코드·테스트를 작성하며, 검증된 결과를 공무원이 이해할 수 있는 문장으로 바꾸는 협업 도구로 사용했다. 범죄·민원 같은 새로운 데이터도 LLM이 임의로 위험도를 판단하게 하지 않고, 사용 목적과 권한을 먼저 데이터 모델로 고정할 계획이다.

**통합 위험 근거층 설계**

- TAAS 사고다발지역을 도로 링크와 결합한다.
- 반복 민원은 개인정보를 제거한 공간·유형·시간대 집계로 만든다.
- 현재와 유사한 과거 기상·교통·계절 조건을 검색해 반복 사건 구간을 찾는다.
- 범죄 통계는 비식별 격자·행정구역 단위의 별도 생활안전 협조층으로 분리한다.

**정확한 주소와 현장 거점 확인**

- 좌표 기반 역지오코딩 API를 연결해 도로명주소·지번·교차로를 검증한다.
- 교래·용담·노형 거점의 현재 운영 여부와 실제 출동 규칙을 기관 자료로 확인한다.
- 차고지 출입구와 도로망 연결점의 스냅 거리도 별도 품질값으로 남긴다.

**기존 제주 플랫폼과의 연계 인터페이스**

- 포트홀·결빙·제설차량 데이터를 어떤 형식과 주기로 받을지 정의한다.
- RoadOps의 우선순위·배분·인계 상태를 기존 상황판에 되돌려주는 API 계약을 설계한다.
- 탐지 시스템 장애와 RoadOps 장애를 분리해 어느 단계에서 보류할지 정한다.

위험을 더 잘 발견하는 시스템과, 발견된 위험을 실제 행정 행동으로 연결하는 시스템 사이에는 무엇이 더 필요할까?
