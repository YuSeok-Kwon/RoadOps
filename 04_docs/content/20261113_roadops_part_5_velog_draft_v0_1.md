지난 작업에서는 제주 실제 도로망과 근무시간·장비·필수 업무를 함께 고려해 `안전 우선`과 `업무 균형` 두 순찰계획을 만들었다. 이번에는 그 계산기를 실제 Agent 흐름으로 연결하고, 도로통제나 폭우가 생겼을 때 영향받은 팀만 다시 계획한 뒤, 결과를 제주 도로 지도 위에서 설명하는 단계까지 진행했다.

처음에는 최적화 결과 JSON이 잘 나오면 Agent가 거의 완성된 줄 알았다. ~~사람이 JSON을 읽는 속도만 빨라지면 될 줄 알았다.~~ 하지만 현장 사용자는 `15,755개 조합을 비교했다`는 말보다 “왜 북부팀 경로만 바뀌었고, 무엇은 그대로 유지됐는가?”를 먼저 알고 싶어 한다.

이번 작업에서 가장 크게 배운 점은 **Agent의 완성도는 답을 한 번 잘 만드는 능력보다, 상황이 바뀌었을 때 기존 약속을 얼마나 안전하게 지키며 수정하는가에서 드러난다**는 것이다.

그래서 RoadOps는 전체 계획을 매번 새로 섞지 않는다. 완료 업무, 운영자가 고정한 업무, 영향받지 않은 팀의 경로는 그대로 보존한다. 통제 링크를 실제로 사용한 팀이나 폭우 영향권에 들어간 팀의 남은 업무만 다시 계산한다. 그리고 변경 전·후 경로, 이동시간 차이와 변경 이유를 같은 지도에서 확인할 수 있게 했다.

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- 자연어 순찰 요청을 7개 Tool로 연결하는 Agent 실행 흐름 구현
- 모든 Tool의 입력·출력·상태·제한사항을 JSONL 감사 로그로 기록
- 도로통제 시 영향팀의 남은 경로만 재계획
- 폭우 What-if 시 위험점수·점검시간·이동시간을 보수적으로 조정
- 완료 업무·고정 업무·비영향팀 계획 보존
- 변경 전후 지표와 한국어 변경 이유 생성
- 제주 표준링크 기반 위험·팀 경로·재계획 지도 구현
- `+0·1·3·6시간`, 안전 우선·균형 운영, 통제·폭우 시나리오 전환
- 점수 상·하한, 근거 충족률, 품질 플래그와 데이터 신선도 표시

**문제 상황**

- 위험점수, 도로망 이동시간, 최적화 모듈은 각각 동작했지만 사용자의 한 문장을 받아 순서대로 실행하는 흐름이 없었다.
- 최초 계획 이후 도로가 통제되면 기존 결과가 더 이상 실행 가능하지 않을 수 있었다.
- 전체 최적화를 다시 돌리면 통제와 상관없는 팀의 방문 순서까지 바뀌어 현장 혼란이 커질 수 있었다.
- 폭우는 실제 관측인지 시연용 가정인지 화면에서 명확히 구분해야 했다.
- 계산 결과가 JSON과 표에만 있어 위험 위치, 팀 경로와 우회 결과를 직관적으로 비교하기 어려웠다.
- 공항·항만 유입압력은 아직 실응답을 확보하지 못했지만 화면을 채우기 위해 임의 값을 넣어서는 안 됐다.

**시도한 방법 & 탐색 과정**

- **먼저 계산 모듈을 7단계 Tool 흐름으로 연결했다.**

대표 요청은 다음처럼 단순하다.

> 팀 3개와 차량 3대로 2시간 안에 현재 위험 기준 순찰계획을 만들어줘. 안전 우선과 업무 균형을 비교해줘.

하지만 Agent 내부에서는 요청을 바로 최적화기에 넣지 않는다.

```text
1. request_interpreter
2. data_quality_gate
3. risk_task_builder
4. travel_time_gate
5. allocation_optimizer
6. plan_validator
7. result_explainer
```

`request_interpreter`는 팀·차량 수, 근무시간, 위험시점과 요청한 대안을 구조화한다. `data_quality_gate`는 사용자 요청과 실제 자원 입력이 맞는지 확인한다. 이후 같은 도로의 이벤트를 현장 작업으로 합치고, 필요한 108개 도로망 경로가 모두 있는지 검사한 뒤에야 최적화를 실행한다.

최적화 결과도 그대로 반환하지 않는다. 별도 `plan_validator`가 작업 중복, 근무시간, 경로 상태, 필수·고정 업무와 장비 조건을 다시 확인한다. 마지막 `result_explainer`는 검증을 통과한 숫자만 사용해 두 대안의 차이와 한계를 설명한다.

- **도로통제에서는 ‘전체 재계획’보다 ‘무엇을 보존할지’를 먼저 정했다.**

이번 데모에서는 동부팀의 첫 업무 1건을 완료 상태로 두고, 다른 업무 1건은 운영자 고정 업무로 설정했다. 통제 링크 `4050025700`은 기존 북부팀의 첫 현장 진입 경로에 포함돼 있었다.

재계획 규칙은 다음 순서로 만들었다.

1. 완료 업무가 팀 방문 순서의 앞부분인지 확인한다.
2. 완료 업무와 운영자 고정 업무를 잠근다.
3. 통제 링크를 사용하는 팀만 영향팀으로 찾는다.
4. 비영향팀의 업무·순서·경로 지문을 고정한다.
5. 영향팀의 남은 근무시간만 계산한다.
6. 통제 링크를 제거한 도로망에서 남은 업무를 다시 최적화한다.
7. 통제 링크 사용, 작업 중복, 근무시간과 고정 업무를 다시 검증한다.

이 방식에서는 북부팀만 재계획 대상이 됐다. 동부팀과 서부팀은 기존 경로를 그대로 유지했다. 방문 업무와 순서는 바뀌지 않고 북부팀의 첫 현장 진입 경로만 우회 경로로 교체됐다.

- **폭우는 관측값처럼 꾸미지 않고 What-if로 분리했다.**

폭우 영향 링크 2개에는 다음 정책 가정을 적용했다.

```text
위험 우선순위 +15점, 최대 100점
현장 점검시간 +10분
영향 링크 통과·도착 이동시간 × 1.25
```

이 숫자는 학습된 계수가 아니라 운영 정책을 시험하기 위한 v0.1 값이다. 그래서 결과 전체에 `what_if_not_observed` 의미를 남기고, 실제 폭우가 발생했다는 문장으로 바꾸지 않았다.

폭우 시나리오에서는 북부팀과 서부팀이 영향팀이 됐다. 두 팀의 남은 업무만 다시 비교한 결과 일부 업무가 서로 교환됐고, 동부팀의 완료·고정·남은 업무는 모두 유지됐다.

- **마지막에는 실제 제주 도로 좌표 위에 결과를 겹쳤다.**

국토교통부 제주 표준링크의 WGS84 형상을 사용해 주요 도로 6,394개 링크를 지도 배경으로 만들었다. 위험예보는 같은 시간·링크별로 묶어 현재·1·3·6시간 각 11개, 총 44개 위험 링크 행으로 정리했다.

지도에는 다음 계층을 함께 올렸다.

```text
주요 제주 도로 배경
현재·1·3·6시간 위험 링크
현장 점검 후보와 필수·제외 조건
동부·북부·서부팀 출발점
안전 우선·균형 운영 배분 경로
도로통제·폭우 영향 링크
부분 재계획 변경 전·후 경로
```

위험 링크를 누르면 우선순위 점수만 보여주지 않는다. 상·하한, 근거 충족률, `exact_link_id` 또는 `spatial_fallback`, 점수 구성요소, 품질 플래그와 대상시각을 함께 표시한다. 근거가 부족한 미래 링크는 0점으로 보이지 않고 `—`로 남는다.

**최종 해결 및 적용 코드**

Agent와 부분 재계획의 핵심은 “계산 → 검증 → 설명”을 분리하는 것이었다.

```python
# RoadOps Agent v0.1 개념 요약

request = request_interpreter(user_text)
quality = data_quality_gate(request, resources, input_reports)
tasks = risk_task_builder(risk_forecasts, constraints)
matrix = travel_time_gate(tasks, road_network)

plans = allocation_optimizer(
    tasks=tasks,
    resources=resources,
    travel_time_matrix=matrix,
)

validated_plans = plan_validator(plans, hard_constraints)
response = result_explainer(validated_plans, limitations)
```

돌발상황이 들어오면 최초 계획 전체를 다시 만드는 대신 영향 범위를 계산한다.

```python
def partial_replan(base_plan, scenario):
    completed = preserve_completed_prefix(base_plan)
    fixed = preserve_operator_fixed_tasks(base_plan)
    affected_teams = detect_affected_teams(base_plan, scenario)
    frozen = freeze_unaffected_teams(base_plan, affected_teams)

    subplan = optimize_remaining_work(
        affected_teams=affected_teams,
        remaining_shift=remaining_shift_minutes(base_plan),
        blocked_links=scenario.blocked_link_ids,
        risk_adjustments=scenario.risk_adjustments,
    )

    result = merge_preserved_and_replanned(completed, fixed, frozen, subplan)
    validate_replanned_result(result)
    return explain_changes(base_plan, result)
```

지도 스냅샷 생성기는 위험·배분·재계획 결과에 실제 링크 형상을 붙인다. 필요한 링크 형상이 없거나 경로 행 전체가 비어 있으면 품질 상태를 `degraded`로 내린다. 화면을 그릴 수 있다는 이유만으로 누락을 통과시키지 않았다.

**개발 중 발견한 실패 사례**

- **전체 재계획의 과잉 변경:** 통제 링크 하나 때문에 모든 팀을 다시 최적화하면 영향받지 않은 팀의 방문 순서도 바뀔 수 있었다. 비영향팀 경로 지문을 고정하고 달라지면 검증 실패로 처리했다.
- **What-if의 사실화:** 폭우 가중치를 적용한 결과가 자연스럽게 보이면서 실제 폭우 관측처럼 읽힐 위험이 있었다. 시나리오 의미와 경고문을 데이터·설명·화면에 모두 남겼다.
- **결측점수의 0점화:** 미래 시점에 근거가 부족한 링크를 0점으로 표시하면 안전한 도로로 오해할 수 있었다. 점수·상하한·근거 충족률을 모두 `—`로 표시했다.
- **오래된 스냅샷의 실시간 착시:** 지도에 표시되면 데이터도 실시간처럼 보였다. 최신 위험 대상시각이 오래됐으면 화면 상단에 `스냅샷 오래됨`을 표시했다.
- **모바일 화면의 빈 공간:** 첫 반응형 검사에서 예측 슬라이더의 flex 기준값 때문에 모바일 상단에 큰 빈 공간이 생겼다. 실제 좁은 화면을 확인한 뒤 행 높이와 중복 시간표시를 수정했다.

### **배운 점 / 재발 방지 노트**

- **부분 재계획은 최적화보다 보존 규칙이 먼저다:** 완료·고정·비영향 업무를 정의하지 않으면 계산상 더 좋은 계획이 현장에서는 더 혼란스러울 수 있다.
- **설명은 모델이 만든 문장이 아니라 검증 결과의 번역이어야 한다:** 변경 이유는 실제 통제 링크 사용 여부와 영향팀 판정에서 만들어져야 한다.
- **지도는 마지막 장식이 아니라 품질검사 도구다:** 숫자만 볼 때 놓친 경로 겹침과 위치 관계가 지도에서는 바로 드러난다.
- **없는 데이터는 화면에서도 없어야 한다:** 공항·항만 유입압력을 임의 값으로 채우지 않고 `데이터 미연결`로 표시했다.
- **‘실시간’은 UI 분위기가 아니라 데이터 시각으로 증명해야 한다:** 저장 스냅샷과 What-if를 라이브 관측으로 표현하지 않는다.

### **새롭게 알게 된 점**

**1. Agent의 핵심은 Tool 개수가 아니라 실패 경계였다**

- 7개 Tool을 연결한 것보다 각 단계가 언제 다음 Tool을 호출하지 말아야 하는지 정하는 일이 더 중요했다.
- 자원 수가 요청과 다르거나 품질보고서가 실패하면 위험 작업 생성 전에 멈춘다.
- 필요한 도로망 경로가 없으면 직선거리로 조용히 대체하지 않고 최적화를 실행하지 않는다.

**2. 최소 변경도 하나의 목적함수였다**

- 통제 후 커버리지와 이동시간만 좋아도 충분하지 않았다.
- 이미 완료한 업무, 고정 업무, 비영향팀 경로를 얼마나 보존했는지도 결과 품질이다.
- 현장에서는 ‘새 최적안’보다 ‘기존 계획에서 무엇이 왜 바뀌었는가’가 더 중요할 수 있다.

**3. 지도에서 신뢰도를 표현하려면 색상만으로 부족했다**

- 위험 단계는 색상으로, 점수 불확실성은 점선으로, 근거 충족률은 투명도로 구분했다.
- 링크 상세에서는 점수 상·하한과 품질 플래그를 같이 보여줬다.
- 위험도와 데이터 신뢰도를 같은 색으로 표현하면 높은 위험과 낮은 신뢰가 섞여 보일 수 있다.

---

### **학습 중 어려웠던 부분**

**부분 재계획의 영향 범위 정하기**

- 통제 링크를 직접 사용하는 팀은 명확했지만 폭우는 현장 위치와 통과 경로 양쪽에 영향을 줄 수 있었다.
- 단순히 영향 링크가 배정된 팀만 찾으면 해당 지역을 지나가는 다른 팀을 놓칠 수 있었다.
- 그래서 `assigned_task_in_heavy_rain_area`와 `route_crosses_heavy_rain_area`를 별도 사유로 남겼다.

**변경 전·후 경로를 한 지도에 표시하기**

- 모든 경로를 진한 실선으로 그리면 제주 도로와 위험 링크가 서로 가려졌다.
- 비영향팀은 낮은 투명도, 변경 전은 회색 점선, 변경 후는 팀 색 실선으로 분리했다.
- 위험 링크는 점수와 근거 충족률에 따라 굵기와 투명도를 다르게 했다.

**실제 서비스와 데모의 경계 표현하기**

- 화면이 완성될수록 현재 기능이 실제 운영 서비스처럼 보였다.
- 하지만 도로시간은 자유흐름 추정이고, 데이터는 저장 스냅샷이며, 폭우·통제는 What-if다.
- 정교한 화면일수록 한계와 승인 절차를 더 눈에 띄게 보여줘야 했다.

---

### **AI를 어떻게 활용했나**

AI는 어떤 팀을 어디로 보낼지 감으로 결정하지 않았다. 대화로 Agent Tool의 책임과 중단 조건, 부분 재계획에서 보존해야 할 상태, 지도에서 보여줄 신뢰도와 신선도 표현을 설계했다. 이후 Python 재계획 로직, 스냅샷 생성기, React 지도 화면을 구현하고 통제·폭우·결측·반응형 실패 사례를 테스트와 화면 검증으로 고정하는 데 활용했다.

위험점수, 도로망 경로, 최적화, 영향팀 판정, 제약 검증과 지표 차이는 모두 결정적인 Python Tool이 계산한다. 현재 자연어 해석도 제출환경에서 재현 가능한 제한 문법이다. LLM은 향후 표현이 다양한 요청을 구조화하고, 검증된 Tool 결과를 사용자의 상황에 맞게 설명하는 층으로 추가할 계획이다.

### **다음에 적용해 볼 것**

**담당자 입력·승인 웹 흐름**

- 지도에서 업무를 고정·제외하거나 팀을 지정할 수 있게 한다.
- 재계획 실행 전 변경 대상과 제약을 미리 보여준다.
- 승인 전에는 현장 지시 상태로 전환되지 않도록 한다.

**실시간 갱신 파이프라인**

- C-ITS·ITS·기상 데이터의 수집시각과 유효시각을 기준으로 지도 스냅샷을 갱신한다.
- 오래된 데이터는 이전 값을 유지하는 대신 명시적인 `stale` 또는 `unavailable` 상태로 보여준다.
- ITS 혼잡을 연결해 자유흐름 이동시간과 실시간 추정시간을 분리한다.

**공항·항만 유입압력 실데이터 연결**

- 승인된 항공·여객선 API의 실제 운항·여객 응답을 다시 검증한다.
- 실응답을 확보하기 전까지 현재의 `데이터 미연결` 상태를 유지한다.
- 연결 후에도 사고확률이 아니라 공항·항만 주변 운영 노출압력으로 별도 표시한다.

**실제 규모 최적화와 사용자 평가**

- 현장 10개를 넘으면 OR-Tools 기반 확장형 엔진으로 전환한다.
- 공무원이 지도만 보고 위험 근거와 변경 이유를 이해할 수 있는지 과업 테스트를 진행한다.
- 안전 우선·업무 균형 중 어떤 지표가 실제 의사결정에 필요한지 피드백을 받아 화면을 줄인다.

계획을 한 번 잘 만드는 Agent와, 상황이 바뀌어도 기존 약속을 지키며 다시 설명하는 Agent 중 실제 현장에서는 어느 쪽이 더 중요할까?
