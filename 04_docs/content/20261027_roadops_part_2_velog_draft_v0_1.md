# [2026-10-27] 제주 RoadOps 프로젝트 2부 — API가 응답했다고 실시간 데이터인 것은 아니었다

## 요약 & 나만의 인사이트

제주 도로의 위험정보와 기상예보를 바탕으로 공무원의 현장 순찰 인력과 차량 배치를 돕는 AI Agent, **RoadOps**를 만들고 있습니다.

지난 기록에서는 국토교통부 전국표준 노드링크에서 제주 노드 27,656개와 링크 37,087개를 추출하고, 실시간 데이터가 들어왔을 때 같은 도로인지 검증할 기준망을 만들었습니다. 다만 당시에는 제주 C-ITS·ITS API 키가 없어 실제 운영 응답의 유효성, 갱신시각, 링크 결합률은 확인하지 못했습니다.

이번에는 C-ITS 4개 API와 ITS 3개 API를 실제로 호출했습니다. 두 인증키는 모두 유효했고 실패 호출은 0건이었습니다. ITS 실시간 교통정보는 12,081건을 반환했고, 최신 데이터는 검사 시점보다 1.498분 전이어서 30분 신선도 기준을 통과했습니다.

하지만 더 중요한 결과는 “API가 잘 열린다”가 아니었습니다.

> HTTP 200과 `success`는 인증 성공을 의미할 뿐, 데이터가 정말 최신이거나 우리 도로망과 정확히 연결된다는 뜻은 아니었습니다.

C-ITS 도로위험정보 33건 중 제주 기준망과 정확히 결합된 것은 24건이었습니다. 도로 작업구간 1건은 기준망에 없었고, 노면기상 12건의 `link_id`는 전부 `-1`이었습니다. 더구나 C-ITS 네 응답에는 관측시각이나 갱신시각이 없어 단일 호출만으로 실시간성을 증명할 수 없었습니다.

이번 작업을 통해 RoadOps의 입력 검증을 `인증 → 응답 구조 → 건수 → 시간 → 도로망 결합`의 다섯 단계로 분리했습니다.

## Part 1. 키가 맞는지와 데이터가 쓸 만한지는 다른 질문이었다

처음 필요한 것은 API 키 유효성 검사였습니다. 그러나 단순히 HTTP 상태 코드만 확인하면 제공자가 오류를 정상 응답 안에 담아 보내는 경우를 놓칠 수 있습니다.

그래서 다음 조건을 모두 통과해야 키가 유효하다고 판단했습니다.

```text
HTTP 200
   ↓
JSON 응답인가?
   ↓
제공자 result가 success인가?
   ↓
예상한 레코드 배열을 추출할 수 있는가?
   ↓
제공 info_cnt와 실제 추출 건수가 같은가?
```

실제 검사 대상은 다음 7개였습니다.

| 구분 | API | RoadOps에서 확인할 내용 |
|---|---|---|
| C-ITS | 도로위험정보 | 사고·낙하물 등 현장 위험 후보 |
| C-ITS | 도로통제정보 | 진입할 수 없는 구간 |
| C-ITS | 도로 작업구간 | 순찰·작업 동선 제약 |
| C-ITS | 노면기상정보 | 결빙·강수·마찰 등 노면 조건 |
| ITS | 실시간 교통정보 | 현재 속도·교통량·통행시간 |
| ITS | 1시간 통계 | 같은 시간대의 단기 기준선 |
| ITS | 일간 통계 | 전일 수준과의 비교 기준 |

C-ITS 키는 4개 API에서, ITS 키는 3개 API에서 각각 검증됐습니다. 모든 응답에서 제공자가 알려준 `info_cnt`와 실제 추출 건수가 일치했습니다. 도로통제정보가 0건이었던 것도 API 실패로 처리하지 않았습니다. 인증과 응답은 정상이지만 검사 시점의 활성 통제 레코드가 없었다는 뜻이기 때문입니다.

## Part 2. 대문자 하나가 실데이터를 0건으로 만들고 있었다

첫 실제 응답에서 바로 파서 문제가 발견됐습니다.

초기 코드는 C-ITS 응답 배열을 대문자 `Info`에서 찾고 있었습니다. 실제 운영 응답은 소문자 `info`를 사용했습니다. API는 정상적으로 데이터를 보내고 있었지만 기존 코드라면 이를 0건으로 해석할 수 있었습니다.

```text
초기 가정: payload["Info"]
실제 응답: payload["info"]
```

이런 문제는 “API 호출 성공” 로그만 봐서는 발견하기 어렵습니다. 응답 건수, 예상 필드, 제공 건수와 추출 건수를 함께 검사해야 알 수 있습니다.

그래서 두 표기를 모두 처리하도록 레코드 추출기를 수정하고, 실제 운영 응답과 같은 소문자 envelope를 자동화 테스트로 고정했습니다. 오류 응답 안에 인증키가 되돌아오더라도 로그에 남지 않도록 제공자 오류 메시지의 키 값도 마스킹했습니다.

## Part 3. 실시간성은 이름이 아니라 시각 차이로 검사했다

API 이름에 “실시간”이 들어간다고 해서 그대로 믿지 않았습니다. ITS 실시간 교통정보의 `prcn_dt`를 파싱해 검사 시점과 직접 비교했습니다.

```text
최신 데이터 나이 = 검사 시각 - 가장 최신 prcn_dt
```

2026년 10월 27일 09:21:29 KST에 실행한 결과는 다음과 같습니다.

| 검사 | 결과 |
|---|---:|
| ITS 실시간 교통 레코드 | 12,081건 |
| 가장 최신 `prcn_dt` | 09:20:00 KST |
| 최신 데이터 지연 | 1.498분 |
| 허용 기준 | 30분 이내 |
| 판정 | 통과 |

1시간 통계는 직전 완료 시간인 08시를 요청했습니다. 12,081건 전부가 요청 시각과 일치했습니다. 일간 통계는 전일인 2026년 10월 26일을 요청했고, 역시 12,081건 전부 요청 일자와 일치했습니다.

반면 C-ITS의 도로위험·통제·작업·노면기상 응답에는 관측시각이나 갱신시각이 없었습니다. 따라서 33건의 위험정보가 지금도 유효한지, 오래된 레코드가 남아 있는지 단일 응답으로는 구분할 수 없습니다.

이 경우 “신선함”으로 판정하지 않고 `not_verifiable`로 남겼습니다. 다음 단계에서는 수집 시각과 스냅샷 해시를 저장하고, 연속 호출에서 레코드의 추가·변경·삭제를 추적할 예정입니다.

## Part 4. ITS는 98.55%가 맞았지만 C-ITS는 그대로 쓸 수 없었다

지난 글에서 만든 제주 기준망 37,087개 링크와 실제 응답의 `link_id`를 정확히 비교했습니다.

| 데이터 | 유효 링크 행 | 정확 결합 | 정확 결합률 |
|---|---:|---:|---:|
| C-ITS 도로위험 | 33 | 24 | 72.73% |
| C-ITS 도로작업 | 1 | 0 | 0.00% |
| C-ITS 노면기상 | 0 | 0 | 측정 불가 |
| ITS 실시간 교통 | 12,081 | 11,906 | 98.55% |
| ITS 1시간 통계 | 12,081 | 11,906 | 98.55% |
| ITS 일간 통계 | 12,081 | 11,906 | 98.55% |

ITS는 사전에 정한 95% 기준을 통과했습니다. 그래도 175개 링크는 기준망과 일치하지 않았습니다. 링크 버전이 다르거나 추출한 기준망 범위 밖일 가능성을 확인해야 합니다.

C-ITS는 더 직접적인 보완이 필요했습니다. 도로위험정보의 정확 결합률은 72.73%였고, 도로작업 1건은 ID가 일치하지 않았습니다. 노면기상 12건은 모두 `link_id=-1`이어서 ID 결합 자체가 불가능했습니다.

노면기상은 데이터를 버릴 문제가 아닙니다. 위도와 경도는 존재하므로 좌표를 기준으로 가장 가까운 도로 링크를 찾을 수 있습니다. 다만 이 결과를 정확 ID 결합과 같은 근거로 취급하면 안 됩니다.

```text
정확한 link_id 일치 → exact_link_id
link_id 불일치 + 좌표 검증 통과 → spatial_fallback
허용 거리 밖 또는 후보 모호 → unmatched
```

현장 자원배분 점수에는 결합 방식과 거리, 후보 수를 함께 전달해 담당자가 근거의 강도를 확인할 수 있도록 할 계획입니다.

## Part 5. 이번 결과가 증명한 것과 증명하지 못한 것

이번 검사로 확인한 것은 다음과 같습니다.

- 두 API 키가 현재 유효하다.
- 설정한 7개 API가 정상 JSON을 반환한다.
- 응답이 보고한 건수와 실제 추출 건수가 일치한다.
- ITS 실시간 교통정보가 30분 기준 안에 들어온다.
- ITS 시간·일간 통계가 요청 기간을 정확히 반환한다.
- ITS 링크의 98.55%가 현재 제주 기준망에 정확히 결합된다.

반대로 다음은 아직 증명하지 못했습니다.

- C-ITS 위험·통제·작업정보가 실제 현장에서도 현재 유효한가
- 미결합 링크 175개가 어떤 버전 차이 때문에 발생했는가
- 좌표 기반 보조 매칭의 적정 거리 임계값은 얼마인가
- C-ITS 이벤트의 위치와 분류가 실제 상황과 일치하는가
- 이 데이터를 이용한 자원배분이 기존 방식보다 나은가

특히 0건을 성공이나 실패로 단정하지 않는 규칙이 중요했습니다. 도로통제 0건은 정상적인 빈 응답일 수 있습니다. 반대로 C-ITS에 시간 필드가 없다는 사실은 데이터가 오래됐다는 증거도, 최신이라는 증거도 아닙니다. 모르는 상태를 별도로 표현해야 합니다.

## AI를 어떻게 활용했나

이번에도 AI를 API 응답의 의미를 임의로 판단하는 도구로 사용하지 않았습니다.

대화로 “키가 작동하는가”라는 질문을 인증, 스키마, 건수, 시간, 도로망 호환성으로 분해했습니다. AI와 함께 실제 응답에서 초기 가정과 다른 구조를 찾고, 소문자 `info` 처리와 제공자 오류 판별, 키 마스킹, 직전 시간·전일 파라미터 생성, 감사 보고서와 자동화 테스트를 구현했습니다.

반면 키 유효성, 최신 데이터 나이, 요청 기간 일치율, 링크 결합률은 Python 코드가 같은 입력에 같은 결과를 내도록 계산합니다. LLM이 “충분히 최신 같다”고 판단하지 않습니다. 30분이라는 기준과 계산식, 실패 상태를 코드에 명시했습니다.

## 현재 완성된 것과 아직 완성되지 않은 것

이번 단계까지 완성된 범위는 다음과 같습니다.

- C-ITS 4개·ITS 3개 운영 API 인증 검사
- 실제 응답의 대소문자 차이를 처리하는 레코드 추출기
- 제공자 오류와 HTTP 오류의 분리
- 인증키를 출력·보고서·오류 메시지에 남기지 않는 안전장치
- `info_cnt`와 실제 추출 건수 일치 검사
- ITS 실시간 데이터 30분 신선도 게이트
- 1시간·일간 통계 요청 기간 일치 검사
- 제주 기준망 37,087개 링크와 실제 응답의 정확 결합률 검사
- 실행 가능한 감사 스크립트와 노트북
- 자동화 테스트 45개

아직 필요한 작업도 분명합니다.

- C-ITS 연속 스냅샷 수집과 변화 추적
- 노면기상·미결합 이벤트의 좌표 기반 공간 결합
- ITS 미결합 175개 링크의 버전 차이 분석
- 평문 HTTP에 의존하지 않는 운영 보안 대책
- 위험점수, 자원배분 목적함수와 기준선 비교

## 배운 점 / 재발 방지 노트

이번 단계에서 얻은 가장 큰 교훈은 “연결 성공”을 데이터 준비 완료로 해석하면 안 된다는 점입니다.

HTTP 200은 네트워크가 응답했다는 뜻입니다. `success`는 제공자가 요청을 받아들였다는 뜻입니다. 레코드 수가 있다는 사실은 데이터가 비어 있지 않다는 뜻입니다. 하지만 최신성, 도로망 호환성, 현장 정확성은 각각 별도의 검사가 필요합니다.

또한 운영 응답은 작은 대소문자 차이 하나만으로도 12,081건을 0건으로 만들 수 있습니다. 앞으로 새로운 API를 연결할 때는 성공 코드뿐 아니라 다음을 함께 고정할 예정입니다.

1. 제공 건수와 추출 건수
2. 실제 필드명과 타입
3. 최신 시각과 허용 지연
4. 기준 키 결합률
5. 빈 응답·오류·판정 불가의 구분
6. 인증정보가 로그에 남지 않는지 여부

다음 작업에서는 C-ITS를 일정 간격으로 수집해 변화 여부를 기록하고, `link_id=-1`인 노면기상과 미결합 이벤트를 도로 형상에 공간 결합합니다. 이 입력 품질을 통과한 뒤에야 위험점수와 순찰 자원배분으로 넘어가겠습니다.
