# [2026-10-27] 제주 RoadOps 프로젝트 2부 — API가 응답했다고 실시간 데이터인 것은 아니었다

### **요약 & 나만의 인사이트**

지난 작업에서 제주 노드 27,656개와 링크 37,087개를 추출하고, 실시간 데이터가 들어오면 같은 도로인지 검증할 기준망을 만들었다. 오늘은 발급받은 C-ITS·ITS 키로 실제 운영 API를 호출해 본 날이다.

C-ITS 4개와 ITS 3개, 총 7개 API가 모두 응답했고 실패 호출은 0건이었다. ITS 실시간 교통정보는 12,081건을 반환했고, 최신 데이터는 검사 시점보다 1.498분 전이었다. 여기까지만 보면 성공적인 하루였다.

~~그런데 HTTP 200이 일을 끝내주지는 않았다.~~

C-ITS 도로위험 33건 중 제주 기준망과 정확히 결합된 것은 24건, 72.73%였다. 도로작업 1건은 기준망에 없었고, 노면기상 12건의 `link_id`는 모두 `-1`이었다. 더군다 C-ITS 응답에는 관측시각이나 갱신시각이 없어 단 한 번의 호출로는 실시간성을 증명할 수 없었다.

오늘의 가장 큰 배움은 **API 연결 성공과 데이터 사용 가능은 다른 판정**이라는 것이었다. 그래서 입력 검증을 `인증 → 응답 구조 → 건수 → 시간 → 도로망 결합`의 다섯 단계로 나누었다.

---

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- C-ITS 4종·ITS 3종 API 키 유효성과 실응답 검사
- 제공자 성공 코드와 실제 레코드 추출 성공 분리
- C-ITS 실응답의 `info` / `Info` 대소문자 호환 문제 수정
- ITS 실시간·시간·일간 데이터의 신선도와 요청 기간 일치 검사
- 37,087개 제주 기준 링크와 운영 응답의 정확 결합률 측정

**문제 상황**

- HTTP 200이어도 제공자가 본문 안에 오류 코드를 담아 보낼 수 있었다.
- 초기 파서는 C-ITS 배열을 대문자 `Info`에서 찾았지만 실제 응답은 소문자 `info`였다.
- API 이름에 “실시간”이 있어도 응답 시각과 관측 시각의 차이를 직접 계산해야 했다.
- C-ITS의 시간 필드 부재와 `link_id=-1`을 오류·0건·실시간 중 하나로 억지 분류하면 안 됐다.

**시도한 방법 & 탐색 과정**

- **키 검사를 HTTP 상태 하나로 끝내지 않았다.**

```text
HTTP 200
   ↓
JSON 응답인가?
   ↓
제공자 result가 success인가?
   ↓
예상한 레코드 배열을 추출할 수 있는가?
   ↓
제공 info_cnt와 추출 건수가 같은가?
```

검사 대상은 C-ITS 도로위험·도로통제·도로작업·노면기상과 ITS 실시간 교통·1시간 통계·일간 통계, 총 7개였다. 모든 응답에서 `info_cnt`와 실제 추출 건수가 일치했다.

도로통제정보 0건은 실패로 보지 않았다. 인증과 응답 구조가 정상이고 제공 건수와 추출 건수가 모두 0이라면, 검사 시점에 활성 통제가 없었다는 뜻으로 분리했다.

- **소문자 한 글자 때문에 0건이 되는 문제를 잡았다.**

```text
초기 가정: payload["Info"]
실제 응답: payload["info"]
```

API는 정상적으로 데이터를 보내고 있었지만, 기존 코드는 전체 응답을 0건으로 읽을 수 있었다. 두 표기를 모두 처리하도록 추출기를 수정하고, 실응답과 같은 소문자 envelope를 테스트로 고정했다. 오류 본문이 인증키를 되돌려줘도 로그에 남지 않도록 마스킹도 추가했다.

- **실시간성을 시각 차이로 계산했다.**

```text
최신 데이터 나이 = 검사 시각 - 가장 최신 prcn_dt
```

2026년 10월 27일 09:21:29 KST에 검사했을 때 최신 `prcn_dt`는 09:20:00 KST였다. 지연은 1.498분으로, 사전에 정한 30분 기준을 통과했다.

1시간 통계는 직전 완료 시간인 08시, 일간 통계는 전일인 2026년 10월 26일을 요청했다. 두 응답 모두 12,081건 전체가 요청 기간과 일치했다.

C-ITS에는 관측시각과 갱신시각이 없었다. 그래서 최신이라고 가정하지 않고 `not_verifiable`로 남겼다. 다음 단계에서 수집 시각과 스냅샷 해시를 저장해 연속 호출 사이의 추가·변경·삭제를 추적하기로 했다.

**최종 해결 및 적용 코드**

실제 운영 응답을 다음 다섯 판정으로 분리했다.

```python
# API 응답 검증 요약

checks = [
    http_and_provider_success,
    envelope_and_schema_valid,
    reported_count_matches_extracted_count,
    timestamp_within_freshness_threshold,
    link_id_matches_reference_network,
]

# 시간 필드가 없으면 True로 가정하지 않는다.
freshness = "not_verifiable" if timestamp_field is None else measured_age
```

**실응답 및 도로망 결합 결과**

| 데이터 | 유효 링크 행 | 정확 결합 | 정확 결합률 |
|---|---:|---:|---:|
| C-ITS 도로위험 | 33 | 24 | 72.73% |
| C-ITS 도로작업 | 1 | 0 | 0.00% |
| C-ITS 노면기상 | 0 | 0 | 측정 불가 |
| ITS 실시간 교통 | 12,081 | 11,906 | 98.55% |
| ITS 1시간 통계 | 12,081 | 11,906 | 98.55% |
| ITS 일간 통계 | 12,081 | 11,906 | 98.55% |

ITS는 사전 기준 95%를 통과했지만 175개 링크는 일치하지 않았다. 링크 버전 차이인지, 제주 기준망 추출 범위 밖인지는 추가 확인이 필요했다.

C-ITS 노면기상 12건은 모두 `link_id=-1`이지만 위·경도는 존재했다. 이 행들을 버리지 않고, 다음 규칙으로 공간 결합하기로 했다.

```text
정확한 link_id 일치               → exact_link_id
link_id 불일치 + 좌표 검증 통과 → spatial_fallback
허용 거리 밖 또는 후보 모호   → unmatched
```

실행 가능한 감사 스크립트와 노트북을 정리했고, 자동화 테스트 45개가 통과했다.

**AI를 어떻게 활용했나**

AI와 “키가 작동하는가?”라는 질문을 인증, 스키마, 건수, 시간, 도로망 호환성으로 분해했다. 실응답에서 초기 가정과 다른 `info` 구조를 찾고, 파서 수정·제공자 오류 판별·키 마스킹·시간 파라미터 생성·회귀 테스트를 구현했다.

최신 데이터 나이와 요청 기간 일치율, 링크 결합률은 Python으로 계산했다. LLM이 “충분히 최신 같다”고 판단하지 않고, 30분이라는 기준과 실패 상태를 코드에 명시했다.

### **배운 점 / 재발 방지 노트**

- **HTTP 200은 시작일 뿐이다:** 네트워크, 제공자 결과, 스키마, 건수, 신선도, 조인은 각각 따로 검사해야 한다.
- **0건에도 이유가 있다:** 정상적인 빈 응답, 인증 실패, 파서 실패를 모두 0건으로 표시하면 운영에서 원인을 찾을 수 없다.
- **실시간은 이름이 아니라 시간 차이다:** 제공자 필드로 관측 시각을 확인할 수 없다면 `not_verifiable`로 남겨야 한다.
- **스키마는 문서보다 실응답을 우선해 검증해야 한다:** 대소문자 하나가 12,081건을 0건으로 만들 수 있다.

### **새롭게 알게 된 점**

**1. API 품질은 단계별 게이트로 봐야 했다**

- `authentication`: 키와 권한이 유효한가?
- `schema`: 예상한 필드와 레코드가 있는가?
- `count`: 제공 건수와 추출 건수가 같은가?
- `freshness`: 관측 시각이 허용 지연 안인가?
- `compatibility`: 기준 도로망과 연결되는가?

이 다섯 단계 중 하나라도 확인할 수 없으면 “준비 완료”로 표시하지 않는 것이 맞았다.

**2. 정확 결합률 98.55%도 만점은 아니었다**

- ITS는 95% 기준을 통과했지만 175개 링크는 여전히 설명해야 할 대상이었다.
- 전체 통과와 예외 목록을 함께 남겨야 버전 차이를 추적할 수 있다.

**3. 시간 필드 부재는 신선함의 증거가 아니었다**

- C-ITS 데이터가 오래됐다는 증거도, 최신이라는 증거도 없었다.
- 이럴 때는 단일 스냅샷을 실시간으로 가정하지 말고 변화 추적으로 보완해야 한다.

### **학습 중 어려웠던 부분**

**성공적인 0건과 실패한 0건 구분**

- 도로통제 0건은 정상일 수 있지만, `Info` / `info` 파싱 오류로 나온 0건은 완전히 다른 문제였다.
- 건수만 보지 않고 제공 상태·응답 구조·제공 건수를 함께 봐야 했다.

**C-ITS의 실시간성 판정**

- 시간 필드가 없으니 숫자로 신선도를 계산할 수 없었다.
- 일단 `not_verifiable`로 두고, 스냅샷 수집 주기와 변경 감지 규칙을 추가하기로 했다.

**노면기상의 `link_id=-1` 처리**

- ID로는 결합할 수 없지만 좌표는 있었다.
- 버리기에는 유용하고, 정확 결합으로 보기에는 근거가 약했다. 공간 보조 결합을 별도 등급으로 두는 이유가 됐다.
