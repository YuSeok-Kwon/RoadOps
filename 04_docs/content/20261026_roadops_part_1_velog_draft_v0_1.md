# [2026-10-26] 제주 RoadOps 프로젝트 1부 — 실시간 데이터가 많다고 바로 순찰계획이 되지는 않았다

## 요약 & 나만의 인사이트

제주 도로의 위험정보와 기상예보를 바탕으로 공무원의 현장 순찰 인력과 차량 배치를 돕는 AI Agent, **RoadOps**를 만들기 시작했습니다.

사용자가 던지는 질문은 단순합니다.

> “오늘 순찰차 4대를 어느 도로에 먼저 보내야 할까?”

하지만 이 질문에 답하려면 먼저 서로 다른 데이터가 정말 같은 도로를 가리키는지 확인해야 합니다. 과거 교통량이 기록된 도로, 실시간 위험상황이 발생한 도로, 통제 중인 도로, 비가 올 것으로 예상되는 지역을 하나의 기준 위에 올리지 못하면 아무리 정교한 배치 알고리즘도 잘못된 입력을 빠르게 처리할 뿐입니다.

이번 단계에서는 위험점수나 경로 최적화부터 만들지 않았습니다. 제주 도로 데이터, C-ITS, 기상청, TAAS를 실제로 어떻게 연결할 수 있는지부터 확인했습니다.

가장 중요한 발견은 공식 명세상 제주 도로 구간과 C-ITS·ITS 데이터가 공통으로 `link_id`를 제공한다는 점이었습니다. 좌표가 가까운 도로를 추정하는 방식보다 훨씬 명확한 1차 결합 기준입니다.

동시에 아직 모르는 것도 분명해졌습니다. 공식 명세에서 필드가 존재한다는 사실과 실제 운영 데이터의 결합률이 높다는 것은 같은 말이 아닙니다. 다만 이번에는 국토교통부 전국표준 노드링크 원본을 확보해 제주 기준망 64,743행을 직접 검증했습니다. C-ITS·ITS API 키가 없어 실시간 응답과의 실제 조인율은 아직 측정하지 못했습니다.

## Part 1. 순찰배치보다 먼저 같은 도로인지 확인해야 했다

RoadOps의 최종 목표는 도로마다 위험 우선순위를 계산하고, 가용한 인력과 차량을 여러 순찰팀에 배정하는 것입니다. 신규 통제나 기상 변화가 생기면 완료된 업무와 담당자가 고정한 업무는 유지하면서 영향받은 팀만 다시 배치하려고 합니다.

처음에는 다음과 같은 흐름을 생각했습니다.

```text
과거 사고·교통량 + 실시간 위험 + 기상예보
                    ↓
              도로별 위험점수
                    ↓
          순찰팀 배정과 방문 순서
```

문제는 첫 번째 화살표였습니다.

실시간 이벤트에 위도와 경도가 있다고 해서 바로 특정 도로에 붙일 수 있는 것은 아닙니다. 교차로에서는 여러 도로가 가깝고, 상하행이나 평행도로를 잘못 고를 수도 있습니다. 좌표계가 다르거나 수집 시점이 어긋나면 가장 가까운 링크가 실제 발생 도로라는 보장도 없습니다.

그래서 첫 작업의 질문을 바꿨습니다.

> “위험한 도로를 계산할 수 있는가?”가 아니라 “각 데이터가 같은 도로를 가리킨다는 것을 감사 가능한 방식으로 증명할 수 있는가?”

## Part 2. 공식 명세에서 공통 연결고리를 찾았다

제주빅데이터센터의 데이터 명세에는 도로 구간, 도로 노드, 일일 교통량, 일·시간대별 교통량이 정의되어 있습니다.

도로 구간에는 `link_id`, 시작 노드, 종료 노드가 있고, 도로 노드에는 `node_id`와 위·경도가 있습니다. 국토교통부 전국표준 노드링크는 원본 선형도 함께 제공하므로, 시작·종료 좌표만을 이어 추정하지 않고 실제 도로 형상을 기준망으로 사용할 수 있습니다. 교통량 데이터도 같은 `link_id`를 제공합니다.

제주 C-ITS의 도로위험상황, 도로통제, 도로 작업구간, 노면기상과 ITS 실시간 교통정보에도 `link_id`가 포함됩니다. 이 구조라면 1차 결합은 좌표 추정이 아니라 정확한 키 조인으로 설계할 수 있습니다.

기상청과 TAAS는 결합 방식이 다릅니다.

| 데이터 | 결합 기준 | RoadOps에서의 역할 |
|---|---|---|
| 제주 도로 구간·노드 | `link_id`, `node_id` | 기준 도로망과 링크 형상 |
| 일별·시간대별 교통량 | `link_id` | 평시 속도와 통행시간 기준선 |
| C-ITS 위험·통제·공사·노면기상 | `link_id`, 위·경도 | 실시간 위험과 운영 제약 |
| ITS 실시간 교통 | `link_id` | 현재 속도·교통량·통행시간 |
| 기상청 초단기예보 | 5km `nx`, `ny` 격자 | 가까운 미래의 지역 기상 조건 |
| TAAS 세부링크 위험지수 | WGS84 `LineString` | 구조적인 도로 위험 사전정보 |

기상청 예보는 도로 링크의 중점 좌표를 5km 격자로 변환해 연결합니다. 개별 도로의 미세기상이라고 해석하지 않고 지역 단위의 외생 변수로 사용합니다. TAAS는 링크의 시작·종료점을 `LineString(경도 위도, 경도 위도)` 형태로 전달해 위험지수를 조회하도록 설계했습니다.

## Part 3. 정확 조인과 공간 조인을 같은 결과로 취급하지 않았다

`link_id`가 있다는 이유만으로 모든 행이 정상일 것이라고 가정하지 않았습니다. 누락, 형식 오류, 링크 버전 차이가 생길 수 있기 때문입니다.

현재 구현한 결합 순서는 다음과 같습니다.

```text
1. link_id가 정확한 10자리 숫자인지 검사한다.
2. 기준 도로망에 같은 link_id가 있으면 exact_link_id로 결합한다.
3. ID가 없거나 일치하지 않을 때만 좌표 기반 공간 보조 매칭을 시도한다.
4. 초기 검증 기준인 100m 밖이면 억지로 붙이지 않고 unmatched로 남긴다.
5. 정확 조인, 공간 보조, 미결합, 유효하지 않은 입력을 각각 집계한다.
```

핵심은 공간 보조 매칭을 성공처럼 숨기지 않는 것입니다. 같은 링크 ID로 연결한 이벤트와 좌표가 가깝다는 이유로 추정한 이벤트는 근거의 강도가 다릅니다. 최종 화면에서도 이 차이를 표시해야 담당자가 결과를 다시 확인할 수 있습니다.

또한 링크 ID가 9자리라고 앞에 0을 임의로 붙이지 않습니다. 잘못된 식별자를 그럴듯한 정상 값으로 바꾸는 대신 유효하지 않은 데이터로 남깁니다.

## Part 4. 세 건의 fixture로 실패 경로부터 고정했다

실제 제주 운영 데이터의 성능처럼 보이지 않도록 고정 예시 데이터(fixture)에는 `illustrative_fixture_not_real_jeju_observations`라는 표시를 넣었습니다.

두 개의 가상 도로 링크와 세 개의 이벤트를 만들었습니다.

| 이벤트 | 결과 | 이유 |
|---|---|---|
| 정상 `link_id`를 가진 이벤트 | 정확 조인 1건 | 기준 도로망과 ID 일치 |
| 존재하지 않는 `link_id`, 링크 위 좌표 | 공간 보조 1건 | 100m 임계값 안의 링크 발견 |
| 도로망에서 멀리 떨어진 좌표 | 미결합 1건 | 가장 가까운 링크도 임계값 초과 |

이 테스트의 결합률 66.7%는 RoadOps의 실제 정확도가 아닙니다. 세 가지 분기가 의도대로 동작하는지 확인하기 위해 만든 결정론적 예시입니다.

이제는 데이터 소스 정의, 응답 구조 해석, 링크·노드 검증, 거리 계산, 기상청 격자 변환을 포함해 자동화 테스트 22개가 통과합니다.

## Part 5. 실제 제주 도로망 64,743행을 검증했다

제주빅데이터센터의 원본 행 데이터는 로그인과 분석실 예약, 센터 내 분석, 반출 승인이 필요했습니다. 공개 다운로드로 바로 재현하기는 어려웠습니다.

대신 2026년 10월 14일자 국토교통부 전국표준 노드링크 ZIP을 받았습니다. 전국 노드 1,184,340개와 링크 1,564,022개에서 광의의 제주 경계를 사용해 노드 27,656개와 링크 37,087개를 추출했습니다. 원본의 ITRF2000 좌표계는 `.prj`를 읽어 WGS84로 변환했고, ZIP SHA-256과 출력 파일 해시를 남겼습니다.

| 검사 | 실제 결과 |
|---|---:|
| 고유하고 유효한 노드 ID | 27,656 / 27,656 |
| 고유하고 유효한 링크 ID | 37,087 / 37,087 |
| 정상 참조된 시작·종료 노드 | 74,174 / 74,174 |
| 유효한 링크 WKT 형상 | 37,087 / 37,087 |
| 유효한 차로 수·제한속도 | 37,087 / 37,087 |
| 최대 연결요소에 포함된 노드 | 27,656 / 27,656 |

사전에 정한 14개 품질 게이트는 모두 통과했습니다. 도로명이 `-`로 된 링크 553개는 오류로 삭제하지 않고, 사용자에게 보여줄 때 링크 ID나 주변 지명을 보완해야 하는 문제로 남겼습니다.

다만 이 100%를 실시간 데이터 결합 정확도로 읽으면 안 됩니다. 유효한 좌표를 가진 노드를 먼저 고르고, 양단 노드가 모두 있는 링크만 남겼기 때문에 좌표와 참조 무결성 100%는 일부분 추출 규칙의 결과입니다. 또한 위도 범위를 보면 제주 본섬 중심이므로, 추자도 등 부속 도서 커버리지는 행정구역 경계와 다시 비교해야 합니다.

## Part 6. 데이터가 공개되어 있어도 바로 운영에 쓸 수 있는 것은 아니었다

공식 소스 9개를 등록하고 문서 접근성을 점검했습니다. 국토교통부 기준망은 공개 다운로드로 확보했고, 제주빅데이터센터의 데이터 명세 파일과 제주 C-ITS·ITS, 기상청, TAAS의 안내 페이지도 접근할 수 있었습니다.

하지만 운영 API 검증은 아직 완료되지 않았습니다. 현재 환경에는 API 키가 없기 때문에 probe는 실제 호출을 수행하지 않고 `credential_missing` 상태를 반환합니다. 키가 없는 상황을 빈 데이터 0건으로 해석하지 않도록 한 것입니다.

더 중요한 문제도 발견했습니다. 제주 C-ITS·ITS 안내 문서에 적힌 운영 API 주소는 평문 HTTP입니다. 현재 환경에서 HTTPS 연결도 확인하지 못했습니다. 쿼리 문자열에 들어가는 키가 노출될 수 있으므로 운영 단계에서는 제공기관의 HTTPS 지원을 다시 확인하고, 백엔드 프록시와 제한된 키, 키 순환 정책이 필요합니다.

이 문제를 해결하지 않은 채 브라우저에서 API를 직접 호출하는 구조는 사용하지 않을 계획입니다.

## AI를 어떻게 활용했나

이번에도 AI를 결론을 대신 정하는 도구로 사용하지 않았습니다.

대화로 문제를 “위험점수 계산”보다 앞선 “데이터 결합 가능성 검증”으로 좁혔고, 공식 데이터 명세와 API 문서에서 필요한 필드를 추적했습니다. 그다음 AI와 함께 데이터 소스 설정, 읽기 전용 접근성 probe, 공간 결합 함수, 실패 사례 테스트를 구현하고 결과를 다시 검토했습니다.

반면 링크 ID 검증, 좌표 거리 계산, 격자 변환, 결합률 집계는 재현 가능한 Python 코드가 담당합니다. 앞으로도 LLM은 공무원의 요청을 구조화하고 결과를 설명하되, 위험점수와 자원배분은 명시적인 규칙과 최적화 코드가 계산하도록 분리할 예정입니다.

## 현재 완성된 것과 아직 완성되지 않은 것

현재 완성된 범위는 다음과 같습니다.

- 제주 도로·C-ITS·ITS·기상청·TAAS 데이터 소스 9개 정의
- 실제 제주 기준망 노드 27,656개·링크 37,087개 추출
- ID·좌표·참조·형상·속성·연결성 14개 품질 게이트 통과
- `link_id` 우선 결합과 거리 임계값 기반 공간 보조 매칭
- 미결합 이벤트를 강제로 배정하지 않는 감사 로그
- WGS84 좌표의 기상청 5km 격자 변환
- TAAS 조회용 도로 링크 `LineString` 생성
- 문서 접근성과 API 키 상태를 분리한 읽기 전용 probe
- 자동화 테스트 22개

아직 완성되지 않은 범위도 분명합니다.

- C-ITS·ITS, 기상청, TAAS 키를 사용한 실제 응답 검증
- 실데이터의 링크 ID 유효율과 정확 조인율 측정
- 제주 본섬·부속도서 행정구역 커버리지 측정
- 위험점수와 자원배분 목적함수 설계
- 단순 우선순위·최근접 배정과의 성능 비교

## 배운 점과 다음에 적용할 것

이번 단계에서 얻은 가장 큰 교훈은 데이터의 개수보다 결합 근거가 먼저라는 점입니다.

공공데이터 API가 여러 개 있다는 사실만으로 하나의 의사결정 시스템이 만들어지지는 않습니다. 같은 도로를 가리키는 키가 있는지, 키가 실패했을 때 어떤 보조 규칙을 쓰는지, 추정 결과를 정확 조인과 구분하는지, API가 실패했을 때 빈 데이터로 오해하지 않는지가 먼저 정해져야 합니다.

다음 단계에서는 실제 API 키로 실시간 응답을 받아 이번에 검증한 기준망과 비교합니다. 유효한 링크 ID 비율, 정확 조인율, 공간 보조 비율, 이벤트 좌표와 링크 사이의 거리 분포를 계산하고 100m라는 초기 임계값도 조정할 예정입니다.

이 기준을 통과한 뒤에야 “어느 도로가 위험한가”와 “어느 팀을 먼저 보내야 하는가”를 계산하겠습니다.
