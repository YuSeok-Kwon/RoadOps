# [2026-10-26] 제주 RoadOps 프로젝트 1부 — 실시간 데이터가 많다고 바로 순찰계획이 되지는 않았다

### **요약 & 나만의 인사이트**

제주 도로의 위험정보와 기상예보를 바탕으로 공무원의 현장 순찰 인력과 차량 배치를 돕는 AI Agent, **RoadOps**를 만들기 시작한 날이다.

사용자의 질문은 단순하다.

> “오늘 순찰차 4대를 어느 도로에 먼저 보내야 할까?”

처음에는 과거 사고·교통량, 실시간 위험상황, 날씨를 모아 가중치를 붙이면 빨리 우선순위를 만들 수 있을 줄 알았다. ~~점수식부터 짜면 오늘 안에 데모까지 나올 줄 알았다.~~

하지만 서로 다른 데이터가 정말 같은 도로를 가리키는지부터 증명하지 못하면, 정교한 점수식도 잘못된 입력을 빠르게 계산할 뿐이었다. 그래서 첫 작업을 위험점수가 아닌 **도로 기준망과 데이터 결합 규칙**으로 바꿨다.

국토교통부 전국표준 노드링크에서 제주 노드 27,656개와 링크 37,087개를 추출했고, 14개 품질 게이트를 모두 통과했다. 그리고 `link_id` 정확 결합과 좌표 기반 공간 보조 결합을 같은 성공으로 취급하지 않는 규칙을 세웠다.

오늘의 결론은 “데이터가 많은가?”가 아니라 **“같은 도로라는 건 어떻게 증명했는가?”**를 먼저 물어야 한다는 것이었다.

---

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- 제주 도로 기준망 추출과 품질 검증
- C-ITS·ITS·기상청·TAAS 데이터의 결합 기준 설계
- `link_id` 정확 결합과 좌표 기반 보조 결합 분리
- 미결합·잘못된 식별자를 억지로 복구하지 않는 규칙 구현
- API 키가 없을 때 빈 데이터와 접근 불가를 구분하는 probe 작성

**문제 상황**

- 실시간 이벤트에 위·경도가 있어도 교차로, 상·하행, 평행도로 중 어디인지 단순 최근접으로는 확정하기 어려웠다.
- `link_id`가 있다고 해도 누락, 형식 오류, 버전 차이가 있을 수 있었다.
- 제주빅데이터센터 원본은 로그인·분석실 예약·반출 승인이 필요해 공개 환경에서 바로 재현하기 어려웠다.
- C-ITS·ITS API 키가 아직 없어 명세상 필드와 실제 운영 응답을 동일하다고 가정할 수 없었다.

**시도한 방법 & 탐색 과정**

- **우선 공통 식별자를 찾았다.**

| 데이터 | 결합 기준 | RoadOps에서의 역할 |
|---|---|---|
| 제주 도로 구간·노드 | `link_id`, `node_id` | 기준 도로망과 링크 형상 |
| 일별·시간대별 교통량 | `link_id` | 평시 속도와 통행시간 기준선 |
| C-ITS 위험·통제·공사·노면기상 | `link_id`, 위·경도 | 실시간 위험과 운영 제약 |
| ITS 실시간 교통 | `link_id` | 현재 속도·교통량·통행시간 |
| 기상청 초단기예보 | 5km `nx`, `ny` | 지역 단위 미래 기상 |
| TAAS 세부링크 위험지수 | WGS84 `LineString` | 구조적 도로위험 선행정보 |

기상청은 도로 링크 중점을 5km 격자로 변환해 연결했다. TAAS는 링크의 시작·종료점을 `LineString(경도 위도, 경도 위도)`로 변환해 조회하는 방식으로 정리했다.

- **정확 결합과 추정 결합을 분리했다.**

```text
1. link_id가 정확한 10자리 숫자인지 검사한다.
2. 기준 도로망에 같은 ID가 있으면 exact_link_id로 결합한다.
3. ID가 없거나 일치하지 않을 때만 공간 보조 매칭을 시도한다.
4. 초기 검증 기준 100m 밖이면 unmatched로 남긴다.
5. 정확·보조·미결합·잘못된 입력을 각각 집계한다.
```

9자리 ID에 0을 임의로 붙여 10자리로 만들지도 않았다. 잘못된 값을 그럴듯한 정상 값으로 바꾸는 것보다 “확인 불가”로 남기는 편이 낫다고 판단했다.

- **실패 경로부터 fixture로 고정했다.**

실제 제주 성능으로 오해하지 않도록 `illustrative_fixture_not_real_jeju_observations`를 표시하고, 정확 결합 1건·공간 보조 1건·미결합 1건을 만들었다. 결합률 66.7%는 실제 정확도가 아니라 세 개의 분기가 의도대로 작동하는지 확인하는 예시였다.

**최종 해결 및 적용 코드**

공개 재현이 가능한 국토교통부 전국표준 노드링크 ZIP을 기준망으로 선택했다. 원본의 ITRF2000 좌표계는 `.prj`를 읽어 WGS84로 변환했고, 원본 ZIP과 출력 파일의 SHA-256을 남겨 다시 같은 기준망을 만들 수 있게 했다.

```python
# 도로 이벤트 결합 규칙 요약

if valid_link_id and link_id in road_network:
    join_method = "exact_link_id"
elif coordinates_are_valid and nearest_distance_m <= 100:
    join_method = "spatial_fallback"
else:
    join_method = "unmatched"

# 결합 방법과 거리를 결과에 같이 보존한다.
```

**실제 제주 도로망 검증 결과**

| 검사 | 실제 결과 |
|---|---:|
| 고유하고 유효한 노드 ID | 27,656 / 27,656 |
| 고유하고 유효한 링크 ID | 37,087 / 37,087 |
| 정상 참조된 시작·종료 노드 | 74,174 / 74,174 |
| 유효한 링크 WKT 형상 | 37,087 / 37,087 |
| 유효한 차로 수·제한속도 | 37,087 / 37,087 |
| 최대 연결요소에 포함된 노드 | 27,656 / 27,656 |

사전에 정한 14개 품질 게이트는 모두 통과했다. 도로명이 `-`로 된 링크 553개는 오류로 삭제하지 않고, 화면에서 링크 ID나 주변 지명을 보완해야 하는 문제로 남겨두었다.

다만 이 100%는 실시간 데이터의 결합 정확도가 아니다. 유효한 노드와 양단 노드가 모두 존재하는 링크를 추출한 결과이다. 제주 본섬 중심의 범위였기 때문에 추자도 등 부속도서는 행정구역 경계와 다시 비교해야 한다.

API 키가 없는 상태는 0건으로 처리하지 않고 `credential_missing`으로 남겼다. 제주 C-ITS·ITS가 평문 HTTP를 사용한다는 점도 별도 위험으로 기록했다. 브라우저에서 인증키를 바로 노출하지 않고, 백엔드 프록시와 키 제한·순환 정책을 사용하기로 했다.

이 단계에서 자동화 테스트 30개가 통과했다.

**AI를 어떻게 활용했나**

AI와 대화하며 “위험점수를 만든다”는 큰 문제를 “데이터가 같은 도로를 가리키는지 검증한다”는 작은 문제로 쪼갰다. 공식 명세서 필드를 추적하고, 데이터 소스 설정·접근성 probe·공간 결합·실패 테스트를 함께 구현했다.

다만 링크 ID 검사, 좌표 거리, 기상청 격자 변환, 결합률은 Python 코드가 같은 입력에 같은 결과를 내도록 했다. 최종 제품에서도 LLM은 요청을 구조화하고 결과를 설명하는 역할을 맡고, 점수와 배치는 명시적 규칙과 최적화 코드가 계산하게 할 예정이다.

### **배운 점 / 재발 방지 노트**

- **데이터 수보다 결합 근거가 먼저다:** API가 여러 개여도 같은 도로라는 근거가 없으면 하나의 의사결정 시스템이 되지 않는다.
- **정확 결합과 추정 결합은 다르다:** 공간 보조 결합을 성공 한 줄로 숨기지 말고 거리와 방법을 남겨야 한다.
- **모르는 값을 정상 값으로 만들지 말자:** ID 보정이나 API 실패를 0건으로 바꾸면 오류가 보이지 않게 된다.
- **100%의 모수를 확인하자:** 기준망 무결성 100%와 실시간 이벤트 결합 정확도 100%는 전혀 다른 의미다.

### **새롭게 알게 된 점**

**1. 도로 링크는 추상적인 ID가 아니었다**

- `link_id`는 교통량, C-ITS, ITS를 연결하는 공통 언어였다.
- 단순한 식별자가 아니라 도로 형상, 시작·종료 노드, 속성 검증의 기준이 됐다.

**2. 좌표 결합은 최근접 거리 하나로 끝나지 않았다**

- 교차로와 양방향 도로에서는 가장 가까운 링크가 실제 도로라는 보장이 없다.
- 거리 임계값, 방향, 후보 간 격차를 다음 버전에서 함께 검토해야 한다.

**3. “접근 불가”도 하나의 데이터 상태였다**

- API 키가 없은 것과 정상 응답이 0건인 것은 다르다.
- 결과만 저장하지 말고 수집 상태와 실패 이유를 함께 보존해야 한다.

---

### **학습 중 어려웠던 부분**

**실제 결합률 없이 설계를 시작한 것**

- 공식 명세에 `link_id`가 있다고 실제 응답도 모두 일치하는 것은 아니다.
- API 키가 없었기 때문에 이번에는 결합 규칙과 실패 상태만 고정하고, 실제 성능 주장은 다음으로 미룠다.

**공개 재현성과 제주 전용 데이터 사이의 균형**

- 제주빅데이터센터 원본이 더 직접적이지만 즉시 다운로드할 수 없었다.
- 일단 공개 재현이 가능한 국토교통부 기준망으로 구조를 만들고, 후속 데이터를 선행정보로 붙이기로 했다.

**평문 HTTP API 사용**

- 키가 쿼리스트링에 들어가는데 HTTPS가 확인되지 않았다.
- 데모를 빨리 만드는 것보다 브라우저 직접 호출을 금지하는 구조를 먼저 정했다.
