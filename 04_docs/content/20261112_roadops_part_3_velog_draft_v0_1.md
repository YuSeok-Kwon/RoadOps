# [2026-11-12] 제주 RoadOps 프로젝트 3부 — 결측을 0점으로 바꾸지 않는 위험점수

### **요약 & 나만의 인사이트**

RoadOps의 첫 위험점수 v0.1을 완성한 날이다. 지난 작업에서 제주 기준 도로망 37,087개 링크와 C-ITS·ITS 운영 API를 연결했으니, 이제 위험 이벤트와 날씨, 교통정보를 합쳐 점수만 만들면 될 줄 알았다. ~~가중치 네 개 정해서 더하면 오후에는 끝날 줄 알았다.~~

막상 시작해 보니 계산식보다 먼저 해결해야 할 문제가 훨씬 많았다. 링크가 없는 노면기상은 어느 도로에 붙여야 하는지, 교통정보가 없는 도로는 0점으로 봐도 되는지, 제주데이터허브와 TAAS처럼 뿌리가 같은 데이터를 두 번 더해도 되는지부터 결정해야 했다.

이번 작업에서 가장 크게 배운 점은 **모르는 값을 낮은 위험으로 바꾸면 안 된다**는 것이다. 데이터가 없다는 이유로 0점을 주면, 정보가 부족한 도로가 안전한 도로로 둔갑한다. 점수를 많이 만드는 것보다 만들면 안 되는 점수를 멈추는 규칙이 먼저였다.

실제 C-ITS 25건 중 점수가 생성된 것은 18건이었다. 나머지 7건은 도로 위치가 모호하거나 근거가 부족해 `hold`로 남겼다. 25건을 억지로 모두 채우지 않았다는 사실이 이번 결과에서 가장 마음에 드는 부분이다.

### **프로젝트: 제주 도로위험 순찰배치 AI Agent — RoadOps**

**오늘 해결한 문제 / 이슈**

- C-ITS 이벤트를 정확 ID 결합·좌표 보조 결합·자동 배제로 분리
- 제주데이터허브·ITS·기상청·TAAS를 이벤트 1건당 1행으로 통합
- 현재 이벤트·구조위험·기상·노면·교통을 분리한 위험점수 설계
- 결측값을 0으로 대체하지 않는 상·하한과 근거 커버리지 구현
- 점수를 사용할 수 있는지 `usable`, `degraded`, `hold`로 판정

**문제 상황**

- 노면기상 12건처럼 `link_id=-1`인 데이터는 ID로 도로를 찾을 수 없었다.
- 좌표상 가장 가까운 도로가 두 개 이상이면 최근접 링크를 무조건 고르는 방식이 위험했다.
- 교통이나 TAAS가 누락됐을 때 0점을 넣으면 데이터 부족이 저위험으로 왜곡됐다.
- 제주데이터허브 ID 1027과 TAAS는 같은 사고 원천에서 파생돼 독립 점수처럼 더하면 중복 계산이 됐다.
- C-ITS에는 제공기관 발생시각이 없어 점수가 계산돼도 정말 현재 상황인지 확인할 수 없었다.

**시도한 방법 & 탐색 과정**

- **도로 결합을 세 단계로 분리했다.**

1. **정확 ID 결합:** 유효한 `link_id`가 기준망에 있고 좌표도 도로 형상과 맞으면 `exact_link_id`로 처리했다.
2. **좌표 보조 결합:** ID가 없을 때 최근접 거리가 30m 이내이고 1·2순위 후보의 거리 차가 5m 이상일 때만 `spatial_fallback`을 허용했다.
3. **자동 배제:** 후보가 모호하거나 좌표가 잘못됐으면 `excluded`로 남기고 점수 입력을 차단했다.

이번 스냅샷 25건은 `exact_link_id` 4건, `spatial_fallback` 15건, `excluded` 6건으로 나뉘었다. 배제 6건 중 5건은 양방향 링크처럼 1·2순위 후보가 너무 가까웠고, 1건은 좌표가 제주 범위를 벗어났다.

- **통합 테이블의 단위를 이벤트 1건당 1행으로 고정했다.**

조인할 때 가장 무서운 건 행이 소리 없이 늘어나는 것이다. 이벤트 1건에 교통·날씨·TAAS가 여러 행씩 붙으면 같은 위험이 반복 계산될 수 있다. 그래서 입력 25건이 최종 출력에서도 25건인지, `event_id`가 모두 고유한지 품질 게이트로 확인했다.

```text
C-ITS 이벤트 25건
  → 도로 결합 등급
  → 제주데이터허브 구조위험
  → ITS 최신 교통
  → 기상청 격자 예보
  → TAAS 링크 위험
  → 통합 이벤트 25건
```

- **위험을 네 가지 질문으로 나눴다.**

| 구성요소 | 최대 가중치 | 확인하는 질문 |
|---|---:|---|
| 현재 이벤트 | 35 | 사고·낙하물·통제·작업이 있는가? |
| 구조위험 | 25 | 과거 사고와 심각도 특성이 있는 도로인가? |
| 기상·노면 | 25 | 강수·바람·시정·마찰·노면온도가 위험한가? |
| 교통 노출 | 15 | 속도와 점유율이 위험 노출을 높이는가? |

노면기상 센서행은 그 자체가 사고나 통제 이벤트가 아니다. 그래서 현재 이벤트 35점을 주지 않고 적용 가능한 구성요소만으로 다시 0~100점으로 환산했다.

**최종 해결 및 적용 코드**

핵심은 점수 하나가 아니라 추정점수·하한·상한·근거 커버리지를 같이 계산하는 것이었다.

```python
# 위험점수 v0.1 핵심 규칙 요약

COMPONENT_WEIGHTS = {
    "event": 35.0,
    "structural": 25.0,
    "weather_road": 25.0,
    "traffic": 15.0,
}

# 현재 확인된 근거만으로 추정점수 계산
estimate = weighted_observed_score / observed_weight

# 빠진 근거가 전부 0점일 때와 100점일 때의 범위
lower_bound = weighted_lower_score / expected_weight
upper_bound = weighted_upper_score / expected_weight

evidence_coverage = observed_weight / expected_weight

if evidence_coverage < 0.60:
    status = "hold"
    risk_score = None
```

교통정보가 없다고 교통을 0점으로 두지 않았다. 대신 해당 구성요소가 만들 수 있는 불확실성을 상·하한에 반영했다. 근거 커버리지가 60% 미만이면 추정점수도 발행하지 않았다.

제주데이터허브 ID 1027과 TAAS의 중복 계산은 하나의 구조위험 25점 안에서 해결했다.

```text
구조위험 = 0.70 × TAAS 등급점수
         + 0.30 × 제주데이터허브 선형 조건부 심각도

구조위험 최대 기여도 = 25점
```

둘 다 사고 관련 데이터라고 25점씩 따로 더하지 않았다. TAAS가 실패하면 제주데이터허브 값만으로 임시 추정하되 구조위험의 근거 커버리지를 30%로 낮췄다.

**실제 실행 결과**

2026년 11월 12일 17:58 KST에 새로 수집한 C-ITS 스냅샷을 사용했다.

| 항목 | 결과 |
|---|---:|
| 입력·출력 | 25 / 25건 |
| 점수 생성 | 18건 |
| `degraded` | 18건 |
| `hold` | 7건 |
| 위험등급 | 높음 1, 보통 14, 낮음 3 |
| 점수 범위 | 10.769 ~ 53.846 |
| 점수 중앙값 | 31.500 |
| 품질 게이트 실패 | 0건 |

점수 18건이 나왔지만 `usable`은 0건이었다. C-ITS에 제공기관 발생시각이 없어서 수집시각으로만 최신성을 판단할 수 있기 때문이다. 계산에는 성공했지만 운영자가 그대로 확정해서는 안 되는 `degraded` 상태로 남겼다.

가장 높은 점수는 516로의 노면기상 행으로 53.846점이었다. 주요 근거는 C-ITS 시정 원시값 `4`, 제한속도 대비 실제속도, TAAS 등급이었다.

그런데 시정 값 `4`의 공식 단위를 찾지 못했다. 현재는 미터라는 임시 가정을 붙였지만, 단위가 확인되기 전까지 운영자가 원시값을 다시 봐야 한다. ~~1등을 뽑았는데 상품을 바로 줄 수 없는 상황이었다.~~

**개발 중 발견한 실패 사례**

- **노면온도 -1 문제:** 처음에는 `-1`을 영하 1도로 읽어 결빙 위험을 높였다. 현재 표본에서는 다른 결측 패턴과 함께 나타나 센서 결측값으로 처리하고 회귀 테스트를 추가했다.
- **오래된 스냅샷 문제:** 첫 실행에서는 C-ITS 스냅샷이 60분을 넘어 모든 행이 `hold`됐다. 코드가 고장 난 줄 알았지만, 오래된 데이터를 막는 안전장치가 정확히 작동한 것이었다.
- **HTTP 200 오류 문제:** 남조로의 한 링크는 TAAS가 HTTP 200을 반환했지만 내부 결과코드는 `INVALID_REQUEST_PARAMETER_ERROR`였다. 전송 성공과 데이터 성공을 분리해 위험값을 0으로 채우지 않았다.

전체 자동화 테스트는 90개가 통과했다. `--as-of`에 같은 시각을 넣으면 동일한 입력에서 같은 점수와 보류 사유가 나오도록 재현성도 고정했다.

### **배운 점 / 재발 방지 노트**

- **결측은 0이 아니다:** 데이터가 없다는 사실은 안전하다는 증거가 아니다. 결측은 점수가 아니라 불확실성으로 표현해야 한다.
- **최근접이 정답은 아니다:** 두 도로 사이에 있는 좌표는 몇 미터 더 가깝다는 이유만으로 자동 배정하면 안 된다. 후보 간 거리 차와 방향 정보를 함께 봐야 한다.
- **출처가 같으면 근거도 겹칠 수 있다:** 이름이 다른 API라고 독립 데이터는 아니다. 원천과 산출 과정을 확인한 뒤 가중치를 묶어야 한다.
- **계산 성공과 사용 가능은 다르다:** 점수가 나왔더라도 시각·단위·결합 근거가 부족하면 `degraded`나 `hold`로 멈춰야 한다.

### **새롭게 알게 된 점**

**1. 위험점수보다 점수 상태가 먼저였다**

- `usable`: 최신성·도로 결합·필수 근거가 모두 확인된 점수
- `degraded`: 계산은 가능하지만 운영자 검토가 필요한 점수
- `hold`: 근거가 부족해 점수 자체를 발행하지 않는 상태

처음에는 0~100점만 만들면 된다고 생각했다. 실제로는 이 점수를 믿어도 되는지를 함께 보여주는 것이 더 중요했다.

**2. 상·하한은 불확실성을 숨기지 않는 가장 단순한 방법이었다**

- 하한은 빠진 근거가 모두 낮은 위험일 때다.
- 상한은 빠진 근거가 모두 높은 위험일 때다.
- 두 값의 간격이 넓으면 데이터가 더 필요하다는 뜻이다.

복잡한 확률모델 없이도 현재 정보가 얼마나 불완전한지 설명할 수 있었다.

**3. 필수 데이터는 많이 쓰는 것보다 제대로 쓰는 것이 중요했다**

제주데이터허브 ID 1027의 실제 51행을 37,087개 링크의 선형 심각도 선행값으로 변환했다. 하지만 사고 발생률로 과장하지 않고, TAAS와 같은 구조위험 바구니 안에서만 사용했다. 공모전 필수 데이터를 넣었다는 사실보다 어떤 한계로 사용했는지를 설명할 수 있게 됐다.

### **학습 중 어려웠던 부분**

**공식 단위가 없는 센서값 처리**

- 시정 원시값 `4`가 4m인지 다른 단위인지 공개 자료만으로 확정할 수 없었다.
- 값이 있으니 일단 쓰자는 유혹이 있었지만, 단위가 틀리면 위험점수 전체가 크게 달라진다.
- 결국 임시 가정 플래그를 남기고 `degraded`로 처리했다. 모르는 것을 코드로 표현하는 일이 생각보다 어려웠다.

**가중치의 근거 설명**

- 35·25·25·15는 학습된 최적 가중치가 아니라 설명 가능한 v0.1 정책값이다.
- 숫자가 만들어지는 순간 정답처럼 보이기 때문에 더 조심해야 했다.
- 현재는 구성요소를 분리하고 상한을 두는 데 집중했다. 다음에는 현장 표본과 민감도 분석으로 조정해야 한다.

**점수 생성과 자원 배분의 경계**

- 위험점수가 높다고 무조건 순찰차를 보내는 것은 아니다.
- 이동시간, 근무시간, 통제구간, 가용 장비가 함께 들어가야 실제 배치안이 된다.
- 이번 단계는 어디를 먼저 검토할지까지이고, 누가 언제 갈지는 다음 단계의 문제로 남겼다.

### **다음에 적용해 볼 것**

**기상 실황과 예보 분리**

- 현재는 기상청 초단기예보에서 실행시각과 가장 가까운 슬롯을 사용한다.
- 다음에는 초단기실황과 예보를 분리하고 `observed_at`, `base_at`, `valid_at`, `fetched_at`을 각각 보존한다.
- 현재·1시간·3시간·6시간 후의 위험 변화를 비교할 수 있도록 시간축을 만든다.

**항공·여객선 유입압력 추가**

- 제주공항 도착편·시간대별 승객과 여객선 일정·통제·정원을 실응답으로 검증한다.
- 편수나 선박 정원을 실제 입도객 수로 부르지 않고 `gateway_inflow_pressure`라는 별도 지표로 관리한다.
- 공항·항만 주변의 교통 노출에는 반영하되 사고위험과 같은 값으로 더하지 않는다.

**제주 도로 지도 웹사이트 구현**

- 도로 링크별 현재 위험과 1·3·6시간 후 예측을 색상으로 표시한다.
- 공항·항만 유입압력, C-ITS 통제·작업, 순찰팀 이동경로를 같은 화면에 올린다.
- 링크를 클릭하면 점수 구성요소, 상·하한, 데이터 갱신시각과 보류 이유를 확인할 수 있게 한다.
